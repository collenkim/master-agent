# master-agent 요구사항과 시스템 설계

요구사항의 기준은 [요구사항 범위와 수용 기준](requirements.md)입니다. 이 문서는 UI·원격 운영을 포함한 제품 설계이며 현재 구현 전체를 뜻하지 않습니다. 로컬 실행 기술은 Node.js·SQLite·LangGraph JS로 구현했습니다. 실제 제공 범위는 [구현 현황](implementation.md), 실행 구조는 [LangGraph](langgraph.md)를 따릅니다. 예산·병렬 개발·원격 배포 정책은 후속 범위입니다.

master-agent의 목적은 여러 프로젝트에 걸친 사용자 목표를 AI가 분석·계획·실행·검증하는 것입니다. 핵심 실행 단위는 목표와 완료 조건을 가진 Mission입니다. master는 프로젝트 선택과 작업 순서를 제안하고, code-agent의 결과를 근거로 다음 행동을 결정합니다. 상세한 상태·계획·재계획 계약은 [AI 오케스트레이션 핵심 설계](orchestration.md)에 정의합니다.

## 1. 초기 범위

초기 제품은 한 사용자의 로컬 환경에서 하나의 다중 프로젝트 목표를 끝까지 처리하는 오케스트레이터입니다. API·CLI로 핵심 흐름을 먼저 검증하고 UI를 연결합니다. 프로젝트 등록과 그룹 관리는 실행 기반이며, 협력 작업과 통합 검증을 최초 제품의 필수 범위에 포함합니다. 다중 사용자 조직 권한과 원격 러너는 확장 범위입니다.

| 요구 | 설계 |
| --- | --- |
| 목표 해석 | 원문·완료 조건·제약·미확정 사항을 구조화 |
| 프로젝트 이해 | 도메인 책임·구현 가능 범위·현재 계획·실행 상태를 구분해 배정 근거로 사용 |
| 판단 후 자동 실행 | 주요 행동의 판단·근거·영향·다음 행동을 먼저 저장하고 실행과 연결 |
| 모호함 재검토 | 추가 분석으로 해소하고 사람의 결정이 필요한 중대한 사안만 요청 |
| 프로젝트 발견과 영향 분석 | 정책·서비스 계약·의존 관계의 출처와 버전에 기반해 대상 제안 |
| 작업 분해와 계획 | 프로젝트별 역할·입출력·선행 조건·검증 기준을 가진 계획 그래프 |
| 실행 조정 | 실행 가능한 노드 배정, 예산·동시성·소유권 검사 |
| 피드백과 재계획 | 발견·실패 분류, 계획 버전 갱신, 영향받는 후행 작업 재평가 |
| 목표 달성 검증 | 개별 검증과 통합 검증을 완료 조건별로 대조 |
| 설치된 프로젝트 목록 관리 | 경로 등록, 지정 폴더의 후보 탐색, 설치 확인, 이름 수정, 보관 처리 |
| 프로젝트 그룹 관리 | 그룹 생성·수정·삭제, 다중 소속, 구성원 추가·제외 |
| 특정 프로젝트 명령 | 프로젝트 상세에서 대상이 고정된 명령 작성 |
| 여러 프로젝트 명령 | 목록의 체크박스로 선택하고 공통 명령 작성 |
| 그룹 명령 | 그룹을 선택한 뒤 실제 대상과 제외 항목 확인 |
| 개별 명령 | 프로젝트마다 서로 다른 지시 또는 공통 지시의 개별 보완 설정 |
| 외부에서 시작한 작업 | code-agent 상태를 관측하되 master 실행 이력과 구별 |
| 진행 상황 | 프로젝트별 단계, 실행 로그, 차단 사유, 질문과 승인 상태 |
| 실패 처리 | 실패한 프로젝트만 새 시도로 재시도하고 기존 결과 보존 |

프로젝트 등록은 저장소에 code-agent를 설치하는 동작과 분리합니다. 설치가 없거나 깨졌다면 이유를 표시하고 명령 실행 대상에서 제외합니다. 등록 해제는 master의 목록만 변경하며 저장소를 삭제하지 않습니다.

## 2. 책임과 구성

```text
목표 입력: CLI / API / UI
  └─ Mission 오케스트레이터
       ├─ AI 판단: 목표 해석 → 영향 분석 → 계획 → 결과 평가·재계획
       ├─ 근거: 프로젝트 카탈로그·정책·서비스 계약·작업 경험
       ├─ 제어: 상태 전이·권한·예산·계획 버전·실행 소유권
       └─ 스케줄러 → 실행 러너 → 프로젝트별 code-agent + 개발 호스트
                  ↑                                  │
                  └── 결과·질문·발견·검증 근거 ──────┘
       └─ 통합 검증 → 완료 조건 판정 → 결과·경험 기록
```

| 구성 요소 | 책임 |
| --- | --- |
| UI·CLI·API | 목표 접수, 판단 입력, 계획·근거·진행 관찰, 범위 안의 수동 제어 |
| master AI 판단 | 목표 해석, 근거 검색, 영향 분석, 계획 제안, 실패 분류와 재계획 제안 |
| master 실행 제어 | 제안 검증, 상태 전이, 권한·예산 검사, 배정, 복구, 완료 조건 검사 |
| 러너 | 프로세스 시작·생존 확인·종료, 출력 수집, 실행 소유권 관리 |
| code-agent | 단일 프로젝트 상태, 개발 절차, 승인 판정, 검증 근거, 재개 판정 |
| 개발 호스트 | code-agent 절차를 따르며 실제 분석·수정·테스트 수행 |

`code-agent` CLI에 자연어 문자열을 전달하는 것만으로 개발이 시작된다고 가정하지 않습니다. 자연어 개발 요청은 개발 호스트의 실행 세션과 연결해야 합니다. master가 프로젝트의 승인·진행 상태 파일을 직접 고쳐 단계를 넘기지 않습니다.

## 3. 프로젝트와 그룹 모델

프로젝트의 실행 위치는 `runnerId + 정규화된 실제 경로`로 구분합니다. 같은 저장소 URL이라도 checkout이 다르면 별도 실행 위치입니다. Windows 경로 대소문자와 심볼릭 링크를 정규화해 같은 위치의 중복 등록을 방지합니다. 프로젝트의 영구 ID는 경로 변경에도 유지합니다.

프로젝트에는 표시 이름, 경로, 저장소 URL, 설치된 호스트, code-agent 실행 파일, 설치 상태, 마지막 조회 시점, 보관 여부를 저장합니다. 도메인 책임·구현 가능 범위·현재 계획·기술 및 계약 제약을 근거와 버전으로 연결합니다. 설치 마커 존재와 JSON 조회 성공 여부를 각각 기록합니다. 전역 실행 파일이 있다는 이유만으로 프로젝트 설치 완료라고 판정하지 않습니다.

초기 그룹은 사용자가 편집하는 평면 목록입니다. 예를 들어 `주문 서비스`에 API·관리자·배치 프로젝트를, `공통 라이브러리 변경`에 관련 프로젝트들을 묶습니다. 하나의 프로젝트를 여러 그룹에 넣을 수 있습니다. 조직 소유권과 접근 권한은 그룹 태그와 별도 모델로 확장합니다.

그룹 삭제는 소속 관계만 지웁니다. 이력에서 참조하는 프로젝트는 보관 처리하며, 실행 중인 대상의 경로 변경·등록 해제는 막습니다.

## 4. 보조 명령과 실행 단위

주 실행 계층은 `Mission → PlanVersion → Task → Attempt`입니다. Task는 분석·계약 정리·프로젝트 구현·통합 검증 등 계획의 작업 노드이며, 한 프로젝트에 여러 Task를 배정할 수 있습니다. Command는 직접 조회·개별·그룹 명령을 받는 보조 입력입니다. 개발 Command는 Mission과 계획으로 정규화하고, 읽기 전용 조회는 Mission 없이 동일 러너를 이용할 수 있습니다.

| 필드 | 의미 |
| --- | --- |
| commandId | 보조 명령 접수 ID. 개발 요청은 missionId와 연결 |
| scope | project / selection / group |
| targetSnapshot | 실행 시 확정한 프로젝트 ID·실행 경로·그룹 버전 |
| mode | broadcast / coordinated |
| instruction | 공통 지시 |
| overrides | 프로젝트별 추가 지시 또는 명시적인 대체 지시 |
| action | 상태 조회 / 설치 점검 / 개발 요청 / 지원되는 재개 동작 |
| taskId | 계획의 한 작업. 실행 위치와 영향을 받는 프로젝트를 구분 |
| attemptId | 해당 작업의 한 번의 실행 시도 |
| idempotencyKey | 같은 접수 요청의 중복 생성 방지 |

공통 지시의 프로젝트별 보완은 기본적으로 추가 지시입니다. 완전히 대체할 때는 화면에 이를 명시하고 최종 지시 전문을 미리 보여 줍니다.

### 같은 명령을 여러 프로젝트에 실행

“커머스 그룹의 현재 작업 상태를 확인해줘”처럼 독립적인 명령입니다. 구성원마다 Task 하나를 생성하고 제한된 수로 병렬 실행합니다. 프로젝트 A가 실패해도 B의 성공 기록을 보존합니다. 재시도 대상은 사용자가 선택하며 성공한 작업을 자동 반복하지 않습니다.

### 프로젝트가 협력하는 작업

“주문 취소 시 결제 환불 후 쿠폰 복구까지 구현해줘”처럼 프로젝트별 역할과 의존 순서가 있는 요청입니다. 계약 합의 → 프로젝트별 구현 → 통합 검증을 계획으로 표현합니다. 의존 그래프는 프로젝트 간 Task 관계이고, 각 프로젝트 내부 단계는 code-agent가 관리합니다.

협력 작업은 최초 제품의 핵심 흐름입니다. AI가 역할과 의존 순서를 제안하고 제어 계층이 계획의 실행 가능성을 검증합니다. 개별·그룹 명령은 이 실행 경로를 재사용하며 독립 실행의 성공 수만으로 목표 완료를 판정하지 않습니다.

### 대상 확정 규칙

명령 작성 중에는 그룹의 현재 구성원을 보여 줍니다. 미리보기 시 대상·지시·설정의 버전을 고정하고 실행 직전에 다시 대조합니다. 바뀌었다면 미리보기를 갱신합니다. 접수된 실행은 그 이후 그룹 구성 변경의 영향을 받지 않습니다.

여러 그룹을 합칠 경우 프로젝트 ID로 중복 제거합니다. 빈 그룹, 모든 대상 제외, 등록 해제된 프로젝트, 설치 불가 상태는 실행 전에 표시합니다. 일부 대상만 실행할 때는 실제 실행 목록을 명시적으로 확정합니다.

## 5. code-agent 연결 계약

읽기 인터페이스는 `code-agent status --json`이며 스키마는 `code-agent.state` v1입니다. 실제 실행은 `code-agent.master` v1의 원자적 접수·위임 판단·이벤트·정지·재부착도 지원합니다([통신 계약](code-agent-control.md)). 아래 표는 읽기 상태 모델이며 CLI의 작업 디렉터리는 등록된 프로젝트 루트입니다.

| 현재 제공 값 | master에서 사용할 위치 |
| --- | --- |
| observedAt, stateVersion | 마지막 관측 시간, 오래된 요청 감지 |
| repo, work, attempt | 저장소·현재 작업·로컬 시도 표시 |
| approval, consents, questions | 승인·사용자 응답이 필요한 작업 모음 |
| verification, findings | 검증 근거와 발견 사항 요약 |
| resume.code, resume.reasons | 재개 가능 여부와 차단 이유 |
| ownership.lease | 프로젝트 작업 소유권 판단 참고 |
| ownership.process | 현재 계약상 unverified이므로 러너의 프로세스 상태와 구별 |

재개 코드는 `stale-request`, `unobservable`, `no-work`, `ownership-conflict`, `wait`, `needs-human`, `replan-required`, `reapproval-required`, `limit-reached`, `ready`입니다. UI에서는 한국어 설명과 원래 코드를 함께 조회할 수 있게 합니다.

`--expect-state`, `--expect-work`, `--expect-attempt`는 조회 결과를 기대 값과 대조하는 옵션이며 조회와 이후 실행을 원자적으로 묶지는 않습니다. 통신 계약의 submit은 같은 잠금 안에서 기대 상태·소유권·임대를 검사합니다. 이 보장은 직접 실행 호스트의 별도 조회·시작에는 적용되지 않습니다.

지원하지 않는 스키마, 잘못된 JSON, 시간 초과, 실행 파일 누락은 서로 다른 연결 오류로 저장합니다. 사람이 읽는 status 문자열을 파싱하는 대체 연결은 두지 않습니다. 프로세스 종료 코드, JSON 스키마 유효성, 로컬 작업 상태를 각각 판정합니다.

읽기 조회가 가능한 것과 개발 실행·승인 전달이 가능한 것은 다릅니다. 프로젝트별 capability를 `status`, `diagnostics`, `submit`, `resume`, `answer`, `cancel`로 구분하고, 실제 연결 시험을 통과한 기능만 활성화합니다. 이 목록은 master의 설계이며 기존 code-agent가 capability API를 제공한다는 뜻이 아닙니다.

## 6. 실행과 복구

프로젝트별 쓰기 작업은 동시에 하나만 허용합니다. 같은 프로젝트에 개별 명령과 그룹 명령이 겹치면 뒤의 요청을 대기열에 넣습니다. 외부 호스트가 작업 중이면 소유권 충돌을 표시하고 자동 탈취하지 않습니다. 조회 작업은 별도의 제한된 동시 실행 수를 사용합니다.

Task 상태는 `queued → running → succeeded / failed / cancelled`를 기본으로 하고 `waiting-input`, `blocked`, `unknown`을 포함합니다. 취소 요청 직후에는 `cancelling`으로 표시하고 실제 프로세스 종료를 확인한 뒤 `cancelled`로 바꿉니다. 취소는 이미 작성된 코드를 되돌리는 동작이 아닙니다.

재시작 시 running 기록을 자동 재실행하지 않습니다. 러너의 실행 식별자·프로세스 시작 시점·소유권과 code-agent 상태를 대조합니다. 확인할 수 없으면 unknown으로 두고 재조회·사용자 확인을 제공합니다. 프로세스 ID만으로 재사용된 다른 프로세스를 종료하지 않습니다.

재시도는 기존 Attempt를 보존하고 새 Attempt를 만듭니다. 결과는 taskId·attemptId·runner 실행 토큰이 현재 시도와 일치할 때만 반영합니다. 늦게 도착한 이전 결과는 이력에 남기되 최신 상태를 덮지 않습니다. 중복 접수 방지는 전체 개발 작업의 정확히 한 번 실행을 보장하지 않습니다.

그룹 실행은 전원 성공, 일부 실패, 전원 실패, 진행 중, 사용자 응답 필요, 취소, 확인 불가를 집계합니다. 독립 실행에서는 성공 수와 실패 수를 보여 주고, 협력 작업에서는 통합 검증을 별도 완료 조건으로 둡니다.

## 7. 저장소와 API 설계

로컬 영속 저장소에는 Mission, AcceptanceCriterion, ScopeSnapshot, PlanVersion, Task, Dependency, Attempt, Artifact, Evidence, Decision, Finding, Budget, Event, StateObservation을 둡니다. 카탈로그는 Project, Group, GroupMember, ServiceContract, KnowledgeReference로 구성하고 보조 명령은 Command로 기록합니다. 계획 버전과 작업·의존 관계의 활성화는 하나의 트랜잭션으로 처리합니다. 실행 시작 의도는 프로세스를 띄우기 전에 저장하고, 시작 직후 중단된 경우 복구 시 대조합니다.

| API 초안 | 역할 |
| --- | --- |
| POST /api/missions | 목표·완료 조건·허용 범위·예산 접수 |
| GET /api/missions/:id | 목표별 계획·진행·근거·차단 이유 |
| GET /api/missions/:id/plans | 계획 버전·의존 관계·재계획 차이 |
| POST /api/missions/:id/decisions | 현재 계획·질문 버전에 묶인 판단 전달 |
| POST /api/missions/:id/pause | 새 배정 중단 요청. 실행 중 작업은 별도 상태로 추적 |
| POST /api/missions/:id/resume | 상태·계획·소유권을 다시 대조한 뒤 재개 |
| GET /api/projects | 목록과 마지막 관측 상태 |
| POST /api/project-candidates | 사용자가 지정한 루트의 설치 후보 탐색 |
| POST /api/projects | 선택한 후보 또는 직접 경로 등록 |
| PATCH /api/projects/:id | 이름·연결 설정 변경 또는 보관 |
| POST /api/projects/:id/observe | 상태 재조회 |
| GET, POST /api/groups | 그룹 목록과 생성 |
| PATCH, DELETE /api/groups/:id | 그룹·소속 변경과 삭제 |
| POST /api/commands/preview | 대상 확정과 프로젝트별 실행 미리보기 |
| POST /api/commands | 미리보기 버전과 중복 방지 키로 접수 |
| GET /api/commands/:id | 전체 실행과 프로젝트별 결과 |
| POST /api/tasks/:id/retry | 선택한 실패 작업의 새 시도 |
| POST /api/tasks/:id/cancel | 취소 요청 |
| GET /api/events | 마지막 이벤트 ID 이후 진행 이벤트 구독 |

질문 응답·승인 전달 API는 기존 호스트의 검증 경로와 연결을 검증한 뒤 추가합니다. UI에 승인 버튼을 먼저 만들고 상태 파일만 바꾸는 구현은 하지 않습니다.

로컬 서버는 loopback에 바인딩하고 Origin·Host 검증과 요청 토큰을 적용합니다. 브라우저가 임의 셸 명령을 서버에 전달하는 API는 두지 않습니다. 프로세스는 명시된 실행 파일과 인자 배열로 시작하고, 자연어는 명령 문자열에 보간하지 않습니다. 토큰·로그 접근은 로컬 사용자 범위로 제한합니다.
