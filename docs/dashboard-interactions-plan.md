# 전체 작업의 질문·선택·승인 요청 대시보드 연동 계획

작성일: 2026-10-19. **설계안이며 아직 구현되지 않았다.** code-agent와 master-agent를 함께 보완해야 한다. 현재 제공 기능은 [대시보드](ui.md), 기존 제어·위임 규칙은 [통신 계약](code-agent-control.md)을 따른다. 아래 신규 API 이름은 제안이며 구현 전 두 저장소에서 계약으로 확정한다.

## 목표와 화면 동작

초기 설정부터 요구 접수·계획·개발·검증·리뷰·반영·복구·운영까지, 사람의 답이나 판단이 필요한 요청을 하나의 대시보드 요청함에서 관제하고 처리한다. master-agent 자체의 질문과 등록 프로젝트의 code-agent 질문을 모두 포함한다. master가 시작하지 않은 독립 code-agent 작업도 연결 권한이 있으면 대상이다. 초기 설정은 이 공통 흐름의 첫 적용 사례다.

1. `응답 필요` 요청함에 발생 주체·그룹/프로젝트·브랜치·진행 단계·TASK 번호(있을 때)·질문·대기 시간·막고 있는 작업을 표시한다. 프로젝트 카드·그룹·목표별 진행 화면에서도 같은 요청으로 이동한다.
2. 일반 선택 질문은 추천안을 첫 번째에 표시하고 기본 선택한다. 추천 이유·확인한 파일/설정 근거·각 대안의 결과를 함께 보여 준다.
3. 사용자는 추천을 유지하거나 다른 선택지·직접 입력을 고른 뒤 `선택 내용 보내기`를 누른다. 기본 선택이나 화면 열람만으로 응답을 전송하지 않는다.
4. 직접 입력이 허용된 질문은 문서 경로·설명 등의 입력란을 표시한다. 다중 선택은 요청에 선언된 선택 개수 제한과 명시적 기본 선택 목록을 따른다.
5. `나중에 결정`은 미해결 대기로 남긴다. 질문 창 닫기·연결 끊김·시간 경과는 답으로 취급하지 않는다.
6. 전송 완료와 실제 적용 완료를 구분한다. 응답이 수신되어도 원래 처리 주체의 적용 결과를 받기 전에는 요청 해결이나 작업 완료로 표시하지 않는다.
7. 문서 확정·계획 승인·반영·업데이트 같은 동의는 일반 업무 선택과 구별한다. 전문과 변경 범위를 보여 주고 승인·거절·수정 요청 등 해당 동의가 지원하는 응답을 명시적으로 받는다. 승인 값을 기본 선택하거나 추천 선택을 승인 영수증으로 바꾸지 않는다.

예시: 기존 프로젝트에 필수 문서가 부족하면 `소스·설정 기준으로 작성 (추천)` / `사용자 선택·입력으로 작성` / `기존 문서 연결`을 제시한다. 기존 문서가 충분하면 근거 경로를 보여 주고 `기존 문서 연결`을 추천한다. 빈 저장소에는 소스 기준 작성을 추천하지 않는다. 이미 사용자가 지정한 방식·경로는 재질문하지 않는다. 이는 현재 code-agent 문서 준비 지침을 화면으로 연결하는 것이다.

추천은 해당 판단을 준비한 주체가 생성한다. code-agent 질문은 code-agent의 조사 근거, master 자체 질문은 master의 계획·운영 근거를 사용한다. 화면은 임의로 첫 옵션을 추천으로 지정하거나 부족한 정책을 채우지 않는다. 추천할 근거가 없으면 이유와 함께 미선택 상태로 질문한다. 앞선 답에 따라 달라지는 후속 질문은 그 답을 받은 뒤 생성한다.

## 처리 대상과 응답 후 동작

| 발생 구간 | 질문·선택·확인 예시 | 응답을 적용할 위치 |
| --- | --- | --- |
| 초기 설정·문서 | 문서 작성/연결 방식, 경로, 구성, 테스트·품질 기준, 문서 확정 | 기존 설정·문서 준비 세션 |
| 접수·분석·계획 | 모호한 요구, 업무 규칙, 대상 프로젝트, 범위·설계 대안, 계획 승인 | 해당 접수·분석·계획 단계 |
| 개발·테스트·리뷰 | 구현 중 추가 질문, 계획 밖 변경, 실패 원인 확인, 환경 조치, 리뷰 판단 | 질문을 낸 작업·검증 회차·리뷰 |
| 반영·인계 | 변경 내용 확인, 반영 동의, 문서 변경 후보, 통합 충돌 처리 | 해당 반영·인계 절차 |
| 장애·복구 | 재시도·추가 허용, 재계획, 중단/계속, 결과 미확인, 재부착 선택 | 기존 복구·판단 처리기 |
| 관제·유지보수 | 업데이트 충돌·버전 선택, 중단 점검, 프로젝트 관리 중 필요한 선택 | 해당 유지보수 작업 |
| master 자체 처리 | 그룹 요청의 대상·완료 조건 보완, 여러 프로젝트의 의존 관계, 사람에게 넘긴 판단 | master 목표·계획·판단 대기 노드 |

단계별로 질문 UI를 따로 만들지 않는다. 공통 요청함과 질문 계약에 단계별 적용 처리기를 연결한다. 오류 로그나 모든 알림을 질문으로 바꾸지는 않는다. 실행 주체가 실제로 사람의 결정을 요구한 경우 요청을 발행하고, 단순 실패·조회 오류는 기존 상태로 표시한다.

처리 권한이 없는 독립 작업·미지원 동의는 요청 내용과 처리할 채널을 표시한다. 권한이 있어 실제로 전송·적용할 수 있는 요청에만 응답 버튼을 제공하며, 지원되는 요청 종류와 처리 가능 여부를 기능 정보로 공개한다. 등록 프로젝트 전체를 수집하고 현재 화면의 필터 때문에 관측을 중단하지 않는다.

## 현재 확인한 연결 공백

| 위치 | 현재 동작 | 필요한 보완 |
| --- | --- | --- |
| master `packages/dashboard/monitor.mjs`, `apps/dashboard/app.mjs` | 질문 ID·답 대기 건수·동의 ID만 표시 | 질문 본문·선택지·추천·입력·제출 UI |
| code-agent `src/agent/choiceServer.ts` | Codex 선택 요청을 stdio MCP elicitation으로 현재 클라이언트에 전달, 대기 응답은 프로세스 메모리에 존재 | 초기 설정도 포함한 영속 요청과 외부 응답 연결 |
| code-agent `src/agent/master/protocol.ts` | 비대화형 Claude master 실행에서 `AskUserQuestion` 제한 | 질문 생성 후 응답 대기·재개를 지원하는 공식 호스트 경로 |
| code-agent `src/agent/master/delegation.ts` | `questions`는 작업/접수 문서 조회, `answer`는 작업 연결·grant·질문 해시를 검사 | 작업 ID가 생기기 전의 설정 질문, 구조화된 추천·후속 질문 처리 |
| code-agent 동의 처리 | setup·docs 등은 사람 전용, 기존 호스트/TTY와 master 위임 출처를 구분 | 대시보드 사람 응답을 위한 명시적인 채널과 적용 검증 |

따라서 master의 기존 `answer`에 `actor: human`만 추가하는 것으로는 초기 설정 전체를 처리할 수 없다. 메모리에만 남은 선택창을 질문 ID 목록으로 복원할 수도 없다. code-agent의 원장 파일을 master가 직접 수정하거나 hook 응답을 만들어 대신 기록하는 방식은 사용하지 않는다.

## 공통 요청·응답 계약

요청을 발행한 주체가 원본을 보관한다. code-agent 요청은 code-agent에, master 자체 질문은 master의 영속 DB에 저장한다. 대시보드는 두 출처를 같은 화면 모델로 표시하되 답은 원래 처리 주체로 보낸다. 요청에는 master 목표·작업 ID가 없어도 된다. 기존 질문·동의·사람 이관 기록을 연결해 동일 요청을 중복 발행하지 않는다.

| 필드 묶음 | 내용 |
| --- | --- |
| 식별·버전 | schemaVersion, source(master/code-agent), sourceInstanceId, requestId, revision, contentHash, 생성/갱신 시각. 출처와 요청 ID를 함께 사용 |
| 대상 | group/project/mission/maintenance 범위와 발행 시 확정한 대상, 해당하는 경우 code-agent 프로젝트·저장소/worktree·브랜치/HEAD·세션 식별자, 선택적인 workId·missionId·taskId·taskNumber |
| 종류·상태 | question/consent/recovery-decision, 발생 단계(setup/document/request/planning/implementation/verification/review/delivery/recovery/maintenance), pending/responded/applied/deferred/expired/cancelled/superseded/failed |
| 질문 | 안정적인 questionId, 제목, 배경, single/multiple/text, 필수 여부, 선택 개수·입력 길이 제한 |
| 선택지 | optionId, 이름, 설명, 선택 결과, 필요한 추가 입력 |
| 추천 | recommendedOptionIds, 추천 이유, 근거 경로·근거 요약. 추천 없음도 표현 |
| 실행 연결 | 원래 실행·세션·재개 위치, 응답을 처리할 소비자, 차단 중인 작업, 응답 가능 여부·불가 사유, 기능 지원 범위 |
| 동의 전용 | consentId, 전문/변경 목록, shownHash, 허용 응답, 사람 전용 여부. 일반 선택 응답과 별도 검증 |

응답은 `commandId`, `requestId`, `expectedRevision`, `contentHash`, 질문별 선택한 optionId 또는 직접 입력을 전달한다. 브라우저에서 프로젝트 경로·실행 명령·답 출처를 임의 지정하지 않는다. 서버가 등록 프로젝트와 연결 정보를 결정한다.

- 같은 commandId와 같은 내용은 동일 결과를 반환하고, 같은 commandId에 다른 내용은 충돌로 거부한다.
- 첫 유효 응답만 수락한다. 두 탭·CLI와 대시보드·두 서버가 동시에 응답하면 원본 요청의 버전으로 중복 적용을 막는다.
- 브랜치·worktree·세션·질문 또는 동의 전문이 달라졌으면 적용하지 않고 새 요청을 확인하도록 한다. 다른 브랜치의 요청을 현재 브랜치에 적용하지 않는다.
- 보류는 업무 답 또는 승인으로 기록하지 않는다. 재개 시 동일 문맥이면 같은 요청을 다시 열고, 문맥이 바뀌면 기존 요청을 superseded로 남긴다.
- 사용자 응답 수신 영수증과 실제 처리 결과를 각각 보존한다. 적용 실패 시 답을 다시 묻거나 새 작업을 중복 생성하지 않고 적용 결과부터 대조한다.
- 그룹 요청은 발행 시 확정한 대상에서 처리한다. 그 뒤 그룹 구성이 바뀌어도 기존 답을 새 구성원에 배포하지 않는다. 한 프로젝트의 답을 다른 프로젝트에 자동 복사하지 않는다.

## code-agent 변경 범위

### 1. 초기 연동과 지원 기능 조회

기존 `master enable`은 문서 확정 전에도 사용할 수 있도록 확인하고, 필요한 최소 설치 상태를 명시한다. 최초 연결·권한 설정은 현재의 사람 TTY 절차를 유지한다. 대시보드에는 미연결 상태와 해당 프로젝트에서 실행할 연결 명령을 표시한다. **최초 신뢰 연결까지 무인으로 처리하는 것은 이번 범위에 포함하지 않는다.** 연결 후 문서 준비와 초기 설정 질문은 대시보드에서 처리할 수 있어야 한다.

대시보드 사람 응답은 개발 자동화 토큰·AI 위임 grant와 구분되는 권한으로 등록한다. 설정/문서 질문 전달을 위해 일반 개발·승인 권한을 확대하지 않는다. 토큰은 저장소 밖에 보관하고 실행 모델·화면에 노출하지 않는다. 소유권 인계·연결 해제 시 이전 응답 권한을 폐기한다.

기존 로컬 CLI 전송과 기능 협상을 확장한다. 제안 명령은 다음과 같다.

| 제안 API | 책임 |
| --- | --- |
| `hello` 기능 정보 | interaction 스키마, 단계별 지원 질문/동의/복구 종류, 사람 채널·독립 세션 응답·초기 설정 지원 여부 |
| `interactions` | 현재 유효한 요청 목록·버전·요약·갱신 커서 |
| `interaction` | 특정 요청의 본문·전체 선택지·추천·필요한 확인 전문 |
| `interaction.respond` | 사람 응답/보류 수락, 버전·문맥·권한 검사, 영수증 반환 |
| `interaction.result` | 응답 수신·소비·적용·재개 결과 및 다음 요청 조회 |

이름과 세부 스키마는 양쪽 저장소의 계약 테스트로 먼저 확정한다. 응답 API는 기존 AI `answer`/`decide`와 구분하고 작업 ID·개발 grant가 없는 초기 문서 세션에도 제한된 사람 응답을 전달할 수 있게 한다.

### 2. 질문 생성과 영속화

- 공통 interaction 저장 계층을 만들고 질문을 화면에 표시하기 전에 원자적으로 저장한다. 변경 이벤트를 공개 상태/이벤트 조회에 포함한다.
- 문서 탐색·작성 방식·기존 문서 경로·신규 구성·테스트/품질 기준 질문을 구조화한다. 기존 questions.md와의 연결을 보존하되 Markdown에서 추천을 추측하지 않는다.
- 요구·설계·구현·검증·리뷰·반영·복구·유지보수의 질문 발생 지점을 조사하고 공통 발행 경로로 연결한다. 기존 질문/동의 ID, 재시도 한도와 실패 근거를 연결하며 화면을 위해 별도 판단 규칙을 만들지 않는다.
- Codex MCP `ask`와 Claude의 일반 질문 생성 경로를 같은 요청 모델에 연결한다. 대시보드 응답과 기존 호스트 응답이 같은 요청에 경쟁할 때 한 번만 수락한다.
- 비대화형 Claude master 실행은 사용할 수 없는 AskUserQuestion을 계속 시도하지 않고 요청을 저장한 뒤 `human-input`으로 대기한다. 모델에 기본값으로 진행하지 않도록 안내한다.
- 이미 열린 기존 선택창 중 내용이 영속화되지 않은 것은 임의 복원하지 않는다. 기존 세션에서 답하거나, 명시적으로 취소 후 새 경로로 재발행한다. 이미 받은 답은 재질문하지 않는다.

### 3. 사람 응답·동의와 재개

일반 질문 답은 `dashboard-human`과 같은 별도 출처로 기록한다. 서버가 전달했다는 사실만으로 기존 호스트가 관찰한 응답(`observed`)이나 승인(`verified`)으로 바꾸지 않는다.

setup/docs뿐 아니라 request/plan/deliver 및 지원되는 운영·복구 동의를 대시보드에서 마무리하려면 code-agent가 이 채널을 공식적으로 지원해야 한다. 기존 사람 확인 모델에 맞춰 신뢰 연결, 전문 해시, 명시적 제출, 일회성 확인, 준비 세션/프로젝트 결합, 만료·취소를 검증한다. 기존 동의 적용 함수와 검사를 재사용한다. 단순 `actor: human` 필드나 HTTP 토큰만으로 검증된 승인 영수증을 발급하지 않는다. 이 채널 검증과 동의 적용 시험이 완료되기 전에는 해당 요청을 기존 사람 채널에서 처리해야 한다고 표시한다. 동작별 지원 여부와 제외 사유를 표로 관리해 초기 설정 동의만 연결하고 전체 완료로 보고하지 않는다.

응답 소비자는 다음 두 경로를 지원한다.

- 살아 있는 호스트 세션: 자신이 발행한 요청의 답을 소비하고 결과를 기록한다.
- 질문을 남기고 종료한 비대화형 실행: 저장된 설정/실행 식별자로 한 번만 재개한다. master 목표가 없는 초기 설정도 재개 가능해야 한다.

답변이 곧 실행 재개를 뜻하지는 않는다. 재시도 선택은 기존 횟수·허용 범위 검사, 재계획 선택은 계획 갱신·재승인, 중단 선택은 기존 협력 정지/취소 경로를 따른다. 외부 실행의 종료가 미확인인 경우 응답 후에도 중복 실행을 시작하지 않는다. 한 요청이 사람을 기다려도 영향을 받지 않는 다른 프로젝트는 계속 진행한다.

대시보드 서버를 켜 놓고 동기 호출 하나를 계속 붙잡는 방식으로 구현하지 않는다. 재시작 후에도 답과 적용 결과를 대조하며, 응답 전송과 실행 시작을 각각 멱등 처리한다. 중단·취소·사용자 보류 상태에서는 자동 재개하지 않는다.

주요 변경 후보: `src/agent/master/{protocol,control,observe,store,runs}.ts`, `choiceServer.ts`, `questions.ts`, `docsCommands.ts`, 동의·검증·복구 처리 모듈, Claude/Codex 각 단계의 질문 템플릿. 각 단계의 기존 적용 경로를 재사용하고 독립 설정·운영 작업을 새 개발 목표로 위장해 실행하지 않는다.

## master-agent 변경 범위

- **어댑터:** 기능 협상과 interaction 조회·응답·결과 API를 추가한다. 미지원 버전은 명확히 표시하고 응답 버튼을 비활성화한다. code-agent 파일에 직접 쓰지 않는다.
- **저장·전송:** 요청 원본 버전과 사용자가 제출한 응답, 전송 commandId, 영수증, 적용 결과를 저장한다. 통신 실패 시 같은 commandId로 결과를 대조한다. 사용자가 편집 중인 선택·입력은 자동 갱신으로 덮지 않는다.
- **요청함:** 전체/그룹/프로젝트/작업·발생 주체·단계·상태 필터, 대기 건수·시간·차단 작업, 질문 상세, 추천 표시·기본 선택·이유·근거, 다른 선택·직접 입력·보류를 제공한다. 새 질문은 배지로 알리고 응답 이력도 조회한다. 그룹에 동일 질문이 있어도 기본적으로 프로젝트별로 답하며 묵시적으로 일괄 응답하지 않는다.
- **master 자체 질문:** 계획 생성·재검토·목표 보완·사람 이관·운영 처리에서 발생한 요청도 같은 저장·응답 서비스를 사용한다. 출처별 적용 처리기로 분기해 master의 답을 code-agent에 보내거나 그 반대로 처리하지 않는다. 기존 AI 위임 판단과 실제 사람 답은 구분한다.
- **상태:** 사람 답 필요 / 전송 중 / 응답 수신 / 적용 중 / 적용 완료 / 보류 / 만료 / 적용 실패를 구분한다. 추천이 선택되어 있다는 이유로 대기 건수를 줄이지 않는다.
- **재개:** 응답 적용을 확인한 뒤 기존 목표·시도·TASK 번호·세션으로 이어간다. 실행기가 이미 살아 있으면 추가 실행기를 시작하지 않는다. 초기 설정 전용 실행과 개발 요청 실행을 구분한다.
- **HTTP:** 인증된 로컬 상세 조회·응답 API를 추가한다. 현재 Host/Origin/토큰 규칙에 새 사람 응답 채널의 권한을 더하고, 허용된 질문 ID·선택지·입력 한도만 받는다. 질문·경로는 HTML로 실행하지 않는다.
- **삭제·업데이트:** 답 전송/적용 중인 프로젝트의 삭제·업데이트와 충돌하지 않도록 한다. 대기 요청이 있는 등록 해제는 외부 질문을 취소하지 않으며, 재등록 시 code-agent 프로젝트 식별자로 다시 조회한다. master 내부 프로젝트 ID만으로 오래된 전송을 새 등록에 재사용하지 않는다.

주요 변경 후보: `packages/code-agent-adapter/`, `packages/dashboard/{monitor,server}.mjs`, 신규 interaction 서비스·저장 기록, `apps/dashboard/{app,index,style}`, 요청 실행기와 진행 상태 투영. UI와 실행 서비스는 동일한 계약을 사용한다.

2~3단계로 일반 선택 화면을 먼저 확인할 수 있지만, 4~5단계까지 통과해야 **전체 단계의 질문·선택·승인 처리가 연결되었다**고 보고한다. 단계/발생 주체/요청 종류별 지원·검증 표를 결과로 남기고 미연결 항목은 명시한다. 초기 설정 성공만으로 전체 연동 완료를 판정하지 않는다. Codex 개발 호스트 추가는 별도 범위이며, 기존 독립 Codex 세션의 질문 연동과 혼동하지 않는다.

필수 검증:

- 추천 기본 선택·추천 변경·직접 경로 입력·다중 선택·부분 응답·보류·후속 질문·추천 근거 없음.
- 기존 문서 연결과 부족한 문서 작성, 빈 저장소 구성 선택, 이미 받은 답의 재사용, 문서 확정의 실제 적용.
- master 목표와 그룹 범위 보완, 개발 중 업무 질문, 검증 실패 후 재시도/재계획/중단, 리뷰 판단, 반영 동의, 업데이트/운영 처리 질문의 실제 적용.
- master가 접수하지 않은 독립 code-agent 작업, 목표 없는 유지보수, 그룹 구성 변경 후 응답 대상 유지, 한 프로젝트 대기 중 다른 프로젝트 진행.
- 브랜치/worktree/세션 불일치, 질문·동의 전문 변경, 허용되지 않은 옵션, 오래된 추천, 취소·만료 뒤 응답 거부.
- 두 탭·호스트와 대시보드 동시 응답, commandId 재전송·충돌, 서버/호스트 종료, 응답 수신 후 적용 전 장애, 같은 설정/작업 한 번만 재개.
- 사람 채널 미등록·권한 폐기·제어권 인계·미지원 code-agent, 질문 내용 HTML 처리, 임의 경로/명령 입력 거부, 비밀값 비노출.
- 프로젝트 삭제·업데이트와 응답 처리 경합, 프로젝트/그룹 필터, 모바일·연결 끊김·편집 내용 유지.
- 실제 모델 두 프로젝트 흐름: 연결 → 초기 문서 추천·확정 → 개발 중 질문·답변 → 검증 실패 판단·복구 → 반영 동의 → 운영 중 질문 처리. master 자체 질문도 포함하며, 각 응답 후 기존 TASK·시도·세션 연결과 중복 실행 부재를 확인한다. 모의 응답만으로 완료 판정하지 않는다.
