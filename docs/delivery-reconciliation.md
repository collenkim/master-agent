# 반영 검증·PR 안내·인계 후 복구

## 반영 증거의 수준

파일 기반 인계는 `local-files`로 기록한다. 테스트를 통과한 파일과 외부 작업 종료를 확인한 것이며 커밋·push·배포를 증명하지 않는다.

배정 전 검증 계약에 다음 선택 항목을 넣으면 `local-commit-with-consent-record` 수준의 인계를 요구한다.

```json
{
  "delivery": {
    "mode": "code-agent-commit",
    "metadataPaths": ["doc/work/MA-example/07-delivery.md"]
  }
}
```

이는 기존 검증 계약에 추가하는 항목이다. 실제 프로젝트의 정확한 반영 기록 경로를 등록하며 경로 패턴이나 디렉터리 전체 허용은 지원하지 않는다. `metadataPaths`는 md·jsonl 파일만 허용한다. 산출물 파일과 정책 근거의 변경은 이 목록에 넣어도 우회할 수 없다.

`mission handoff`와 drive는 다음 조건을 대조한다.

1. 기존 독립 검증과 같은 작업·시도이고, code-agent의 작업·접수·동의·임대가 종료됐다.
2. 검증 시점 HEAD를 부모로 하는 단일 반영 커밋이며 작업 트리와 인덱스가 깨끗하다. merge 커밋과 중간 커밋이 여러 개인 인계는 현재 지원하지 않는다.
3. 검증 이후 변경은 등록된 기록 파일과 `.code-agent/approvals/<작업ID>/consents.jsonl`(검증 계약의 `codeAgentRecords: true`면 그 작업의 code-agent 기록 폴더까지)에 한정된다. 검증 산출물은 변경할 수 없다.
4. 해당 커밋에서 직접 읽은 영수증에 현재 실행 세션·작업 경로·시도 시작 이후 시각과 결합된 deliver/this-commit 항목이 하나 존재한다. 그 항목은 사람의 선택 기록(observed)을 갖거나, `master-delegation` 통로의 위임 영수증이어야 한다 — 위임 영수증은 이 시도의 deliver 위임 판단(승인·적용 완료)과 판단 ID·확인 요청 ID·작업 ID가 같고 사람 응답이 섞이지 않아야 한다([code-agent 통신 계약 연동](code-agent-control.md#위임-판단)).
5. 반영 검사 판단을 저장한 다음 기존 검증 명령을 모두 다시 실행한다. 전후 파일·HEAD·선행 산출물·원격 종료 상태가 유지돼야 인계한다.

반영 동의 JSONL이 손상됐거나 객체 형식이 아니면 `invalid-delivery-receipt`로 거부하고 증거·잠금을 유지한다.

code-agent의 `consentReceipts.ts`에 정의된 커밋 내 기록 형식을 읽는다. 영수증은 로컬 감사 자료이며 전자 서명이나 독립적인 사용자 신원 인증이 아니다. master가 승인·영수증을 생성하거나 커밋·push·배포하지 않는다. 위임 판단도 code-agent가 권한 범위를 확인하고 같은 반영 절차로 커밋·영수증을 만든다. 실제 기존 승인 절차는 code-agent가 담당한다. TTY 반영 등 해당 형식의 this-commit 영수증이 없는 경로는 이 계약을 통과하지 못한다.

`mission show`의 `deliveries`에는 커밋·부모·영수증 해시·변경 목록·후검증 결과가, `evidence[].delivery`에는 증거 수준이 표시된다. 후검증 성공 기록은 봉인해 인계 저장 실패 후 재사용할 수 있다. 후검증 실행 중 오류·시간 초과·관측 실패는 unknown으로 보존하고 잠금을 해제하지 않는다.

## 호스트 반환 후 관측 중단 복구

호스트 호출마다 `invocationId`를 새로 부여한다. CLI가 정상 결과를 반환하면 원격 상태를 조회하기 전에 `host-return`을 영속 저장한다. 늦게 도착한 이전 호출의 결과는 새 호출에 적용하지 않는다.

```powershell
master-agent mission reconcile <목표ID> <시도ID> --revision <현재버전> --expect-state <상태버전> --control
```

대상은 unknown 상태이고 배정 기준·검증 계약을 가진 시도다. 프로세스 중단으로 running만 남았다면 기존 `mission unknown`으로 먼저 미확인 상태를 기록한다. 이는 프로세스 종료를 증명하지 않는다.

reconcile은 현재 invocation의 봉인된 정상 반환, 동일 code-agent 작업과 세션, 승인·질문·동의 상태, 현재 트리에 결합된 code-agent check/test, 활성 실행 임대 없음, 허용된 파일 변경과 기준 HEAD를 대조한다. 통과하면 잠금을 유지한 채 `awaiting-verification`으로 이동한다. 호스트를 다시 실행하지 않으며 독립 검증이 끝나기 전 `continue`도 금지한다. 이후 `mission verify` 또는 drive로 진행한다.

반환 기록이 없거나 이전 호출의 기록뿐인 경우, 검증·반영 검사 프로세스가 running/unknown으로 남은 경우, 외부 작업이 이미 사라진 경우, 임대 충돌·파일 범위 변경·일시 정지는 복구하지 않는다. 이 경로는 호스트가 반환했지만 관측·저장이 중단된 경우에 한정된다. 읽기 전용 분석 예약과 정상 반환된 검증의 중단은 [분석·검증 중단 처리](interruption.md)를 따른다. 관리 실행의 정지·취소는 [code-agent 통신 계약 연동](code-agent-control.md#정지취소)을 따른다. 상태 파일을 직접 수정하는 우회 절차도 제공하지 않는다.

## 목표 단위 PR 안내

`master-agent mission pr <목표ID>`와 대시보드 목표 화면에서 프로젝트별 PR 준비 상태·실제 브랜치·마지막 반영 커밋·squash 메시지를 확인한다. 모든 작업이 인계되고 커밋 연결과 브랜치를 확인해야 PR 준비 완료다. `taskNumber`가 있는 것만으로 `task/<번호>`를 안내하지 않는다. task 요청이 완료되고 실제 로컬 ref가 최종 반영 커밋을 정확히 가리킬 때 사용한다. 미지원·실패·미처리, 없거나 오래된 task 브랜치이면 사유와 함께 최종 커밋을 가리키는 실제 `feature/MA-…`·`fix/MA-…` 등의 작업 브랜치를 안내한다. 적절한 브랜치를 확인할 수 없으면 PR 준비 미완료다. 조회 결과는 그 시점의 로컬 ref 상태이며 push를 증명하지 않는다.

메시지는 `[<TASK 번호>] <목표>` 제목, code-agent 작업 ID·목표·반영 커밋 12자, 완료 조건, 검사 통과 결과를 담는다. TASK 번호가 없으면 제목은 대괄호 없이 `<목표>`이며 실제 작업 브랜치를 사용한다. 작업별 상세 경로는 `doc/work/<codeAgentWorkId>/10-pr.md`다. `local-files` 인계가 있으면 반영 커밋 없음과 PR 준비 미완료를 표시하고 task-branch를 호출하지 않는다. 파일의 HEAD 값을 작업 반영 커밋으로 승격하지 않는다.

## 인계 후 브랜치 복구

인계 이벤트와 브랜치 요청을 같은 트랜잭션에 저장하고 Git 요청은 커밋 이후에 보낸다. 인계 저장 직후 프로세스가 종료돼도 미처리 요청이 남는다. 응답 후 결과 저장이 끊긴 경우도 동일한 commandId로 복구한다. 요청 대상·payload·처리 상태는 기존 Store의 명령 기록과 이벤트에 남고 봉인된 인계 증거·delivery-run은 변경하지 않는다. drive·engine·그래프는 이 복구를 담당하지 않는다.

| 목표 화면 상태 | 조치 |
| --- | --- |
| 미처리 / 응답 확인 필요 | `mission task-branch <목표ID> --control`로 같은 commandId를 재전송한다. 조회 자체는 재전송하지 않는다. |
| 미지원 | 안내된 실제 작업 브랜치로 PR을 만든다. 지원 버전을 연결한 뒤 전용 복구 명령으로 다시 시도할 수 있다. |
| 실패 | 오류 사유를 해결한다. 확정 거부 응답은 같은 ID로 바뀌지 않으므로 `--new-command`로 새 요청을 명시한다. |
| 완료 | 실제 브랜치 상태를 다시 조회하고 현재 안내된 PR 브랜치를 사용한다. 과거 완료 기록만으로 현재 ref를 신뢰하지 않는다. |
| 뒤 작업으로 대체 | 이전 요청은 전송하지 않는다. 최신 인계의 브랜치 요청 상태를 확인한다. |
| 생략 | TASK 번호가 없거나 유효한 작업 반영 커밋이 없다. 작업 브랜치 또는 반영 절차를 확인한다. |

복구는 최신 인계를 먼저 처리하고 이전 미처리 요청은 뒤 작업으로 대체한다. 기능 확인 중 새 인계가 생겨도 이전 요청을 전송하지 않는다. 기존 task ref가 대상 커밋의 조상이 아니면 전송 전에 충돌로 기록한다. 응답 유실 요청은 `--new-command`가 있어도 동일 ID를 유지한다. 실제 ref 갱신 계약은 [task 브랜치 연동](code-agent-control.md#같은-목표프로젝트의-작업-연결과-task-브랜치)을 따른다.

인계 이벤트를 정리한 과거 기록은 명령 기록에 보존된 순번을 사용한다. 둘 다 없는 오래된 인계는 순서를 추측하지 않고 기록 확인을 요구한다.

시험 범위와 실제 연동의 미검증 항목은 [검증 기준](verification.md)을 따른다.
