# master-agent 구현 단계와 완료 기준

최초 제품은 UI 없이 하나의 다중 프로젝트 목표를 접수하고, AI가 프로젝트를 찾아 계획·배정·재계획·통합 검증하는 흐름을 완성합니다. 프로젝트 관리와 개별·그룹 명령 UI는 이 핵심 흐름에 연결합니다.

[요구사항 REQ-01~17](requirements.md)을 기준으로 실행 기반과 근거 수집·AI 분석 연결을 구축했습니다. 아래 전체 제품 계획과 현재 구현 범위를 구별하며, 운영 정책·수치·복구 방식은 상세화하지 않습니다. 실행 방법은 [사용법](usage.md), 수행한 검증은 [검증 기록](verification.md)에 정리했습니다.

## 현재 구현과 다음 작업

현재 구현은 Node.js ESM·SQLite 저장, 프로젝트·그룹·목표 관리, 근거 수집, Codex·Claude CLI 분석과 계획 검증, 자동 재검토·질문 응답, 모의 실행, code-agent 상태 조회와 Claude 개발 호스트 배정·세션 재개입니다. 정확한 변경 파일·독립 검증 명령·산출물의 계약을 등록하고, 실제 검증·로컬 인계·잠금 해제·후행 작업 진행과 목표 완료까지 연결합니다.

호스트 계약은 [개발 호스트 연결](live-execution.md), 검증·후행 작업 연결은 [실제 검증과 자동 진행](live-verification.md), 실패 원인 분석·동일 세션 수정은 [자동 복구](recovery.md)에 정리했습니다. 외부 작업 정리와 연결한 [재계획 인계](replanning.md)도 구현했습니다. [반영 기록·관측 복구](delivery-reconciliation.md)를 연결했습니다. [분석·검증 중단 처리](interruption.md)로 분석 적용 취소와 정상 반환된 검증의 복구를 확장했습니다. 이후 외부 승인 위임·실행 중 취소·미반환 프로세스 복구와 관제 UI를 연결합니다. 추가 파일의 자율 탐색·카탈로그 자동 갱신·업무별 판단 품질 평가 확장은 별도 작업입니다.

## 1. 제안 저장소 구조

```text
master-agent/
  README.md
  docs/
    architecture.md
    requirements.md
    orchestration.md
    ui.md
    implementation.md
  apps/
    cli/                   목표 접수·진행 조회·판단·재개
    web/                   목표·계획·근거·개입 중심 UI
    server/                Mission API와 이벤트 구독
  packages/
    domain/                Mission·계획 버전·작업·증거·판단 모델
    catalog/               프로젝트·서비스·그룹·계약 참조
    knowledge/             범위가 제한된 정책·계약·경험 검색
    reasoning/             AI 목표 분석·계획·결과 평가·재계획
    storage/               영속 저장·마이그레이션
    orchestrator/          상태 전이·계획 검증·스케줄러·예산·복구
    verification/          조건별 증거 검사·통합 검증·완료 판정
    runner/                프로세스·소유권·로그·취소
    code-agent-adapter/    JSON 조회·호스트 연결·기능 확인
    contracts/             API와 이벤트 스키마
  tests/
    fixtures/              가짜 code-agent와 임시 프로젝트
    integration/           실제 API·러너·저장소 연동 시험
```

위 트리는 전체 제품의 목표 구조입니다. 현재 apps/cli와 packages/domain·storage·catalog·knowledge·reasoning·orchestrator·runner·code-agent-adapter·verification을 구현했습니다. tests에는 실행 기반·CLI·AI 분석·호스트·실제 테스트 검증·인계·자동 진행 회귀 테스트가 있습니다. web·server는 아직 없습니다.

LangGraph JS가 자동 진행·계획 재검토·복구·재계획·모의 실행을 담당합니다. Node 내장 SQLite에 기존 도메인 기록과 영속 그래프 체크포인트를 저장합니다. CLI 모델 provider와 검증기는 도메인 서비스로 유지합니다. [LangGraph 실행 구조](langgraph.md)를 참고하세요. 모델 API SDK와 UI 프레임워크는 도입하지 않았습니다.

## 2. 단계별 결과

| 단계 | 구현 범위 | 완료 기준 |
| --- | --- | --- |
| 1 실행 계약과 골격 | Mission·계획·작업·증거·판단 스키마, 영속 상태 전이, 가짜 러너 | CLI에서 계획 실행·중단·재개, 잘못된 상태 전이 거부 |
| 2 AI 분석과 계획 | 최소 카탈로그, 근거 검색, 목표·영향 분석, 구조화한 계획, 계획 검증기 | 목표만 입력해 근거 있는 프로젝트별 계획 생성, 순환·허구 참조·조건 누락 거부 |
| 3 실제 개발 연결 | code-agent 상태, 개발 호스트 실행·질문·승인·결과 계약 | 임시 프로젝트에서 실제 요청과 판단이 기존 code-agent 절차로 수행 |
| 4 핵심 오케스트레이션 완성 | 다중 프로젝트 배정, 예산·잠금, 발견·재계획, 통합 검증, 복구 | 세 프로젝트 목표를 자동 분해·수행하고 계약 변경·실패·재시작을 처리해 근거로 완료 판정 |
| 5 관찰·개입 UI와 보조 명령 | 목표 작업 공간, 계획 그래프, 판단함, 프로젝트·그룹 관리, 직접 명령 | 동일 Mission·Task 계약을 사용하며 수동 개입도 계획·증거에 반영 |
| 6 조직과 외부 연결 | 조직·부서 권한, 원격 러너, 공유 예산, Jira·Notion | 실행·검색·응답에서 권한 경계가 일관되며 외부 동기화 실패가 로컬 결과를 훼손하지 않음 |

요구사항을 구현 순서에 연결할 때 단계 2에는 프로젝트의 도메인·구현 가능 범위·기존 계획 분석(REQ-01~06)을 포함합니다. 단계 1~4에는 판단 기록 후 자동 실행, 모호함 재검토와 중대한 결정 요청(REQ-10~15)을 공통 계약으로 적용합니다. 단계 4~5는 전체 사이클과 프로젝트별 상태 관제(REQ-07~09), 보조 제어(REQ-16~17)를 검증합니다. 이 표의 운영 관련 항목은 세부 조건을 확정한 뒤 구현 범위를 조정합니다.

**단계 1~4가 최초 오케스트레이션 제품의 필수 범위**입니다. 단계별로 내부 기능을 확인하되 카탈로그·조회·명령 전달만으로 목표를 달성했다고 보지 않습니다. 사용자 요청 전체의 UI·그룹·개별 제어까지 충족하려면 단계 5도 완료해야 합니다.

## 3. code-agent와 연결할 때 먼저 해결할 항목

현재 `status --json` 출력과 기대 상태 대조를 재사용합니다. 다음 항목은 별도 연결 시험과 계약 보완이 필요합니다.

1. 개발 호스트에 새 요청을 접수하는 방법과 프로젝트별 호스트 실행 설정.
2. master의 missionId·planVersion·taskId·attemptId와 code-agent 작업·시도·호스트 세션의 상관관계. 직접 명령은 commandId도 연결.
3. 질문과 동의 요청을 UI로 전달하고 답변을 기존 확인 절차에 되돌리는 방법.
4. 상태 조회 이후 실제 재개 시점까지 기대 상태·lease 검증을 유지하는 방법.
5. 호스트 자식 프로세스까지 종료를 확인하는 취소와 재시작 복구.

초기에는 지원 가능한 호스트 조합 하나를 검증한 후 확장합니다. 지원하지 않는 조합은 상태 조회만 제공하고 실행 기능을 명시적으로 비활성화합니다. code-agent 소스 변경은 별도의 변경 범위로 관리합니다.

## 4. 검증 시나리오

임시 프로젝트 세 개와 실패·지연·손상 출력을 제어할 수 있는 가짜 실행 파일을 사용합니다. 실제 개발 실행 시험은 사용 중인 저장소 대신 전용 임시 저장소에서 수행합니다.

핵심 평가는 [오케스트레이션 제품 시나리오](orchestration.md#9-첫-번째-제품-검증-시나리오)를 따릅니다. AI 평가에는 목표·카탈로그·기대 완료 조건을 고정한 사례를 두고, 문장 일치 대신 대상 선택의 근거·필수 조건 누락·범위 위반·잘못된 완료 판정을 검사합니다. 제어 계층은 가짜 모델의 불량 출력으로 검증하고, 실제 모델·호스트 연결 시험은 별도로 기록합니다.

- 근거 없는 프로젝트 선택과 존재하지 않는 계약 참조를 거부하는가.
- 도메인 책임·구현 가능 범위·현재 계획을 대조해 배정하고 프로젝트 측 분석 결과가 다르면 조정하는가.
- 주요 실행 전에 판단이 저장되고 실행이 해당 판단을 참조하는가. 판단 기록 실패나 적용 조건 변경 시 재검토하는가.
- 일반적인 모호함은 근거를 찾아 자동 해결하고 중대한 사람 판단만 대안·영향·권고안과 함께 요청하는가.
- 모든 등록 프로젝트의 상태와 관측 불가 범위를 구분하며 현재 단계·대기 이유·다음 행동을 조회할 수 있는가.
- 계획에 순환 또는 검증되지 않는 필수 완료 조건이 있으면 실행 전에 차단하는가.
- AI가 범위 확대·승인 생략·한도 초과를 제안해도 실행 규칙이 유지되는가.
- 계약 변경 시 관련 후행 작업과 완료 증거만 재평가하는가.
- 개별 테스트가 통과해도 통합 검증 실패 시 Mission을 완료하지 않는가.
- 재계획·수정 반복 한도를 초과하면 중단하고 근거를 남기는가.
- 병렬 배정의 예산 예약과 실제 사용량 정산이 중복되지 않는가.

- 같은 경로의 표기 차이·심볼릭 링크로 프로젝트를 중복 등록할 수 없는가.
- 프로젝트 설치 없음·호환 불가·조회 시간 초과를 작업 실패와 구별하는가.
- 그룹 미리보기 후 구성원이 바뀌면 대상 재확인을 요구하는가.
- 접수 후 그룹이 바뀌어도 기존 실행의 프로젝트 목록이 유지되는가.
- 같은 중복 방지 키로 재전송해도 Command·Task가 하나씩만 생기는가.
- 그룹 명령과 개별 명령이 같은 프로젝트를 동시에 수정하지 않는가.
- 세 대상 중 하나가 실패해도 다른 결과를 보존하며 그 대상만 재시도하는가.
- 재시도 후 이전 시도의 늦은 종료 이벤트가 현재 결과를 덮지 않는가.
- 서버가 프로세스 시작 전후에 중단돼도 확인 불가 상태를 자동 성공·자동 재실행으로 바꾸지 않는가.
- 취소 요청 이후 실제 종료를 관측해야 취소 완료로 바뀌는가.
- 오래된 질문·승인·재개 요청이 현재 작업에 적용되지 않는가.
- 로그와 지시문에 HTML·셸 특수문자가 있어도 화면 코드나 명령으로 실행되지 않는가.
- 이벤트 재연결 후 누락·중복 없이 프로젝트별 진행을 복원하는가.

## 5. 구현 단계의 확인 범위

블로그 구상과 로컬 code-agent 소스를 토대로 실행 기반을 구현했습니다. 실제 code-agent CLI의 상태 조회와 Claude의 근거 기반 계획 생성을 확인했습니다. 별도 합성 Git 저장소에 실제 code-agent를 설치해 Claude 개발 호스트의 응답·권한 차단·관제 기록까지 검증했습니다. 기존 업무 프로젝트는 수정하지 않았고, 실제 코드 수정·테스트·승인 위임의 전체 사이클은 아직 검증하지 않았습니다. 단계별 연결을 전체 AI 오케스트레이션 제품 완성으로 보지 않습니다.
