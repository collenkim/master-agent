# AI 오케스트레이션 핵심 설계

master-agent는 사용자가 전달한 목표를 여러 프로젝트의 작업으로 분해하고, 실행 결과를 해석해 다음 행동을 결정하는 시스템입니다. 사용자는 목표와 제약을 전달하고, master는 관련 프로젝트 탐색부터 통합 검증까지 조정합니다. 프로젝트별 개발 절차는 code-agent가 담당합니다.

제품 요구의 기준은 [요구사항 범위](requirements.md)입니다. 운영 조건은 현재 보류하며 이 문서의 예산·한도·복구 세부 내용은 향후 검토할 설계 후보입니다.

## 1. 목표와 완료 조건

최상위 실행 단위를 Mission으로 정의합니다. Mission은 요청 원문, 구조화한 목표, 완료 조건, 허용된 검색·수정 범위, 제외 범위, 시간·비용·재시도 한도와 결과를 가집니다. 프로젝트 목록은 목표 분석의 결과일 수 있으므로 요청 시 반드시 지정할 필요는 없습니다.

예를 들어 “출고 전 주문을 취소하면 환불하고 쿠폰을 복구해줘”라는 목표를 받으면 주문·결제·쿠폰의 정책과 연결 계약을 찾아 참여 프로젝트를 제안합니다. “환불 요청 접수”와 “환불 확정”처럼 해석에 따라 결과가 달라지는 업무 조건은 근거로 해결하거나 필요한 질문으로 남깁니다.

완료 조건마다 검증 방법과 요구 증거를 연결합니다. 위 목표에서는 출고 전 취소 가능, 환불 확정 후 쿠폰 복구, 중복 이벤트 처리, 실패 후 재처리 등 요청과 정책에서 도출한 조건을 계획에 포함합니다. 예시는 설계 설명이며 실제 업무 정책을 확정하는 값은 아닙니다.

## 2. AI 판단과 실행 제어

AI는 해석·추론·계획·분류에 사용하고, 실행 가능 여부와 상태 변경은 명시적인 코드 규칙으로 검증합니다. AI가 반환한 JSON이나 완료 문장 자체는 승인 또는 검증 근거가 아닙니다.

| 역할 | 입력 | 출력 | 제어 계층의 검사 |
| --- | --- | --- | --- |
| 목표 분석 | 요청, 사용자 제약, 관련 정책 | 목표·완료 조건·질문 | 원문 보존, 조건 누락·모순 |
| 영향 분석 | 카탈로그, 계약, 제한된 문서 검색 | 후보 프로젝트·영향·근거 | 실제 ID, 접근 범위, 출처·버전 |
| 계획 | 목표, 영향, 실행 기능, 예산 | 버전 있는 작업 그래프 | 순환·누락·범위·의존 산출물·검증 노드 |
| 결과 평가 | 구조화한 결과·발견·증거 | 수용·수정·재계획 제안 | 증거 유효성, 현재 시도·계획 일치 |
| 재계획 | 실패·새 발견, 이전 계획 | 변경된 작업·의존 관계·이유 | 변경 범위, 기존 승인·증거 영향, 한도 |
| 최종 설명 | 조건별 검증 결과 | 달성 내용·미달 내용·결과 요약 | 모든 필수 조건 충족 여부 |

이 역할들은 논리적 역할입니다. 역할마다 별도 상주 에이전트가 필요한 것은 아니며, 초기에는 단일 오케스트레이터가 필요한 판단을 순차 호출합니다. 병렬화는 독립성이 확인된 분석·프로젝트 작업에 적용합니다. 모델·프롬프트·도구 스키마 버전과 입력 근거 참조를 기록해 판단을 추적합니다.

모델 출력은 정해진 스키마로 검증합니다. 형식 오류나 존재하지 않는 프로젝트 참조는 제한된 수정 요청으로 처리하고, 수정 한도를 넘으면 차단 사유를 남깁니다. 임의 도구 호출이나 권한 확대 요청을 그대로 실행하지 않습니다.

주요 실행에는 먼저 저장된 Decision을 연결합니다. Decision은 자동 판단과 사람 판단을 구분하며 요구·근거 버전·대안·선택 이유·영향·미확정 사항·다음 행동·검증 방법을 포함합니다. 판단 기록 저장과 적용 조건 검사를 통과하면 자동 실행합니다. 기록만 작성하고 실행과 연결하지 않는 동작은 요구사항을 충족하지 않습니다.

## 3. 프로젝트를 찾는 지식 구조

프로젝트 카탈로그에는 실행 경로 외에 제공 기능, 담당 서비스, 소유자, API·이벤트·스키마 계약, 의존 프로젝트, 문서 위치와 확인된 버전을 연결합니다. 필드는 출처와 관측 시각을 포함하고, 자동 추출한 후보와 검토된 사실을 구분합니다.

프로젝트 이해에는 도메인 책임 경계, 구현 가능한 변경과 제약, 현재 계획·예정된 변경·기존 배정도 포함합니다. 도메인 적합성, 기술적 구현 가능성, 지금 실행할 수 있는 상태를 따로 평가합니다. 부족한 정보는 프로젝트 분석 작업으로 보완하고 배정안이 실제 조건과 다르면 전체 계획을 조정합니다.

검색은 허용 범위 결정 → 서비스·기능 후보 탐색 → 정책·계약 조회 → 관련 구현·검증 근거 조회 순서로 좁힙니다. 검색 결과에는 문서 ID·버전·기준 커밋·참조 위치를 포함합니다. 오래된 문서와 서로 충돌하는 정책은 영향 분석의 불확실성으로 기록합니다. 경험은 해결 방법의 후보이며 필수 정책을 대체하지 않습니다.

그룹은 기본 검색 범위와 작업 범위를 지정하는 수단입니다. 그룹에 속한다는 이유로 모든 프로젝트에 작업을 배정하지 않습니다. AI가 관련 프로젝트를 고르되, 허용 범위 밖 의존성을 발견하면 발견 사항으로 보고하고 범위 확대가 필요한지 판단을 받습니다. 동적으로 발견한 프로젝트를 기존 승인 대상에 조용히 추가하지 않습니다.

초기 지식 입력은 프로젝트에 있는 버전 관리 문서와 명시적인 계약 목록으로 시작합니다. 검색 구현과 저장 매체는 교체 가능하게 두며, 지식 저장소와 실행 상태 저장소는 책임을 분리합니다.

## 4. 계획과 작업 계약

PlanVersion은 목표·완료 조건·범위·정책·계약 버전과 연결된 변경 불가능한 계획 스냅샷입니다. 재계획은 새 버전을 생성하고 이전 버전을 보존합니다. 한 버전의 의존 관계는 순환이 없는 작업 그래프로 제한하며, 반복 수정은 새 시도 또는 새 계획 버전으로 표현합니다.

| Task 필드 | 의미 |
| --- | --- |
| kind | analysis / contract / implementation / verification / integration |
| projectId, executionTarget | 작업 책임 프로젝트와 실제 실행 위치. 통합 검증은 별도 실행 위치 가능 |
| goal, acceptanceCriteria | 해당 작업의 목표와 검증할 조건 ID |
| allowedChanges, exclusions | 수정할 수 있는 범위와 제외 사항 |
| inputs | 선행 작업 산출물 ID·버전·해시 및 정책·계약 참조 |
| outputs | 요구하는 변경·문서·검증 결과의 형식 |
| dependencies | 선행 Task와 요구 산출물·상태 |
| requiredCapabilities | 호스트·러너·code-agent에 필요한 기능 |
| budget, retryPolicy | 시간·비용·호출·재시도 한도 |
| decisionBindings | 적용되는 사용자 판단과 계획·계약 버전 |

작업 요청은 missionId, planVersion, taskId, attemptId, expectedState, 실행 소유권 토큰을 포함합니다. 결과는 status, artifactRefs, evidenceRefs, findings, questions, usage와 같은 식별자를 반환합니다. 이는 **master가 구현할 어댑터 계약**이며 기존 code-agent CLI가 이미 이 전체 형식을 제공한다는 뜻이 아닙니다.

계획 검증기는 모든 필수 완료 조건에 검증 작업이 연결돼 있는지, 선행 산출물이 정의돼 있는지, 존재하는 실행 위치와 기능으로 수행 가능한지 확인합니다. AI의 자연어 계획만으로 배정을 시작하지 않습니다.

## 5. 오케스트레이션 상태 흐름

```text
접수 → 목표 정리 → 근거 수집·영향 분석 → 계획 생성 → 계획 검증
                                                  │
                              필요한 판단 대기 ←──┤
                                                  ↓
실행 가능한 작업 선택 → 배정 → 결과·질문·발견 수집 → 결과 평가
          ↑                                          │
          ├── 같은 계획의 다음 작업 ──────────────────┤
          ├── 허용된 재시도 ──────────────────────────┤
          └── 새 계획 검증 ← 재계획 ──────────────────┤
                                                     ↓
                         통합 검증 → 완료 조건 판정 → 결과 기록
```

현재 Mission 상태는 `received`, `analyzing`, `planned`, `waiting-decision`, `executing`, `paused`, `blocked`, `succeeded`, `simulation-complete`, `cancelled`다. Task·Attempt·러너 상태와 화면의 progress 표시는 별도로 관리한다. 일부 작업이 성공했어도 목표는 실행·대기·차단 상태일 수 있다.

종료 전 목표는 실행 중(`running`) 시도가 없을 때 `mission cancel`로 `cancelled`에 전이한다. 실행 중 시도는 `mission stop` 또는 `mission unknown`으로 먼저 정리한다. 취소는 잠금·분석·복구 보류를 해제하고 결정·사용자 사유를 기록한다. `succeeded`, `simulation-complete`, `cancelled`에서 다시 취소하는 전이는 거부한다.

스케줄러는 선행 작업과 산출물 유효성, 현재 계획 버전, 권한, 예산, 프로젝트 잠금, 러너 용량을 검사한 뒤 배정합니다. 준비된 독립 작업만 병렬 실행합니다. 다른 작업의 실패가 영향을 주지 않는 작업은 정책상 허용되면 계속할 수 있습니다.

LangGraph JS가 영속 체크포인트를 사용해 실행 흐름을 관리합니다. 도메인 트랜잭션·시도 ID·권한 검증·프로젝트 잠금은 외부 작업의 중복 실행과 잘못된 승인을 차단합니다. [LangGraph 실행 구조와 재시작 규칙](langgraph.md)을 참고하세요.

## 6. 발견과 실패에 따른 다음 행동

| 관측 결과 | 기본 처리 |
| --- | --- |
| 일시적 연결 실패, 부작용 없음 확인 | 정해진 한도 안에서 재시도 |
| 실행했는지 알 수 없음 | 상태·산출물 대조 후 결정, 확인 전 중복 배정 금지 |
| 허용 범위 안의 코드 결함 | code-agent의 기존 수정·검증 경로 수행 |
| 로컬 테스트 실패 | 근거를 전달해 제한된 수정 시도, 반복되면 원인 재평가 |
| 공유 계약·타 프로젝트 영향 | 관련 후행 배정 보류, 영향 분석과 재계획 |
| 요구·업무 정책 불명확 | 추가 근거와 프로젝트 분석으로 재검토, 사람의 결정이 필요한 중대한 사안만 질문 |
| 무관한 개선 발견 | 후속 후보로 기록하며 현재 목표와 분리 |
| 예산·수정·재계획 한도 초과 | blocked로 전환하고 사용량·필요 조치 제시 |

재계획은 변경된 계약·입력에 의존하는 작업을 추적합니다. 영향을 받는 완료 작업의 증거는 오래된 것으로 표시하고 재검증하거나 새 작업으로 대체합니다. 영향이 없는 완료 작업과 증거는 재사용합니다. 영향받는 실행 중 작업은 추가 배정을 막고 취소 또는 결과 격리를 수행합니다. 이전 계획 결과는 그대로 현재 계획에 수용하지 않습니다.

수동 개별 명령으로 프로젝트가 바뀌어도 같은 영향 재평가를 수행합니다. 실행 중인 Mission에 대한 변경 지시는 기존 계획에 끼워 넣지 않고 변경 제안과 새 PlanVersion으로 처리합니다.

## 7. 자율 수행과 사람의 판단

기본 원칙은 근거 있는 자율 판단과 실행입니다. 허용된 탐색·계획·배정·검증·수정은 판단 내용을 기록한 뒤 자동 진행합니다. 모호함은 추가 검색·프로젝트 분석·정책 대조·대안 비교로 재검토합니다. 해소 가능한 문제마다 사용자에게 결정을 넘기지 않습니다. 실행 정책의 운영 수치와 세부 조건은 나중에 정합니다.

재검토로도 AI가 결정할 수 없는 중대한 사안만 사람에게 결정 요청을 올리는 것이 제품 목표입니다. 기술적 정보 부족으로 인한 차단·복구 요청은 중대한 의사결정과 구분합니다. 기존 code-agent의 필수 승인과 제품 목표 사이의 차이는 연동 과제로 관리합니다. master의 자동 판단 기록은 기존 필수 승인을 대체하지 않으며, 위임이 필요하면 프로젝트 측 검증 계약을 별도 설계합니다.

Decision에는 결정자·질문·계획·계약 버전·허용 범위·응답·시각을 저장한다. 적용 시 버전과 조건을 다시 대조한다. `mission pause`는 새 배정을 멈추고, `mission stop`은 특정 관리 실행의 종료를 요청한다. `mission cancel`은 실행 중 시도가 없는 목표를 마감하며 작성한 코드를 되돌리지 않는다. 완료 검증은 [검증 기록](verification.md)과 [실제 검증 계약](live-verification.md)을 따른다.
