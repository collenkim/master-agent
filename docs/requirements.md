# master-agent 요구사항 범위

master-agent는 여러 프로젝트의 도메인·책임·구현 가능 범위와 현재 계획을 이해하고, 요구사항을 분석·세분화해 적합한 프로젝트에 업무를 배분하며, 개발 전체 사이클을 진행하는 AI 관제 센터다. 프로젝트 그룹과 특정 프로젝트를 대상으로 사용할 수 있다. AI는 판단 내용을 명확하게 정리한 뒤 자동 실행하고, 모호한 사항은 재검토하며, 사람이 결정해야 하는 중대한 사안만 판단을 요청한다.

이 문서는 사용자가 정한 제품 목표와 자율 수행 원칙의 기준이다. 아래의 세부 동작과 수용 기준은 이를 구현 가능한 요구사항으로 풀어 쓴 설계안이다. 운영 조건은 이번 상세화 범위에서 제외한다. 기존 문서의 운영·기술 선택은 확정 요구사항으로 취급하지 않는다.

## 1. 대상과 요구사항 해석

**REQ-01 대상 범위:** 하나의 프로젝트, 선택한 여러 프로젝트, 하나 또는 여러 그룹을 대상으로 요청할 수 있어야 한다. 그룹 구성원이라는 이유만으로 모두 수정하지 않고 요구와 역할에 맞는 참여 프로젝트를 선정한다. 요청 대상과 실제 배정 대상, 추가 영향 대상은 구별한다.

**REQ-02 요구사항 분석:** 원문에서 목표, 세부 요구, 완료 조건, 제약, 제외 사항, 모호한 사항을 도출한다. 각 세부 요구는 원문과 연결하며 분석 중 추가한 해석·가정·확인된 사실을 구별한다. 사용자가 프로젝트별 구현 지시까지 작성하지 않아도 업무를 나눌 수 있어야 한다.

**REQ-03 요구사항 추적:** `원문 → 세부 요구 → 프로젝트 역할 → 계획 작업 → 구현 결과 → 검증 근거`를 추적한다. 배정되지 않은 요구, 중복된 책임, 검증되지 않은 완료 조건을 식별한다. 요구가 변경되면 영향을 받는 계획·작업·검증 결과를 다시 평가한다.

수용 기준: 다중 그룹 요청에서 중복 프로젝트를 구분하고, 요구와 관련된 프로젝트만 근거를 붙여 선정한다. 모든 필수 세부 요구에 책임 작업과 검증 방법이 연결돼야 한다.

## 2. 프로젝트 이해와 업무 배분

**REQ-04 프로젝트 이해:** 프로젝트별로 다음 내용을 근거와 함께 유지한다.

| 이해 항목 | 필요한 내용 |
| --- | --- |
| 도메인과 책임 | 담당 업무, 책임지는 기능·데이터, 다른 프로젝트가 담당하는 경계 |
| 구현 가능 범위 | 현재 구현, 지원 가능한 변경, 기술·계약 제약, 추가 조사가 필요한 부분 |
| 연계 관계 | 제공·소비 API와 이벤트, 공유 스키마, 선행·후행 의존성 |
| 현재 계획 | 진행 중 목표와 승인·확정된 계획, 예정된 변경, 기존 배정 |
| 실행 가능성 | code-agent 연결, 필요한 호스트 기능, 작업 가능·대기·충돌·미확인 상태 |
| 근거와 불확실성 | 문서·코드·검증 참조와 버전, 상충하는 정보, 미확인 가정 |

도메인 적합성과 실행 가능성은 따로 판단한다. 도구가 실행 가능하다는 이유만으로 해당 프로젝트에 업무 책임이 있다고 판단하지 않는다. 정보가 부족하면 프로젝트별 읽기·분석 작업으로 먼저 확인한다.

**REQ-05 명확한 업무 배분:** 각 작업에 책임 프로젝트, 배정 이유, 달성할 요구, 수정 범위, 제외 범위, 입력, 산출물, 선행 조건, 연계 프로젝트, 완료 조건을 지정한다. 공동 작업에도 산출물별 책임을 명확히 둔다. 현재 프로젝트 계획과 충돌하면 신규 작업을 그대로 밀어 넣지 않고 병합·순서 조정·재계획의 근거를 정리한다.

**REQ-06 프로젝트 측 실행 가능성 확인:** 배정안에 대해 프로젝트의 현재 상태와 분석 결과를 대조하고 수행 가능·추가 분석 필요·계약 조정 필요·수행 불가를 구별한다. master의 추정과 프로젝트의 실제 조건이 다르면 계획을 수정한다. 모든 배정에 사람의 사전 확인을 요구하지 않는다.

수용 기준: 같은 요구에 여러 프로젝트가 관련되더라도 누가 무엇을 구현하고 어떤 결과를 넘기는지 설명할 수 있어야 한다. 다른 프로젝트가 책임지는 기능을 중복 구현하거나 기존 계획과 충돌하는 배정을 검출해야 한다.

## 3. 개발 전체 사이클 관제

**REQ-07 사이클 진행:** 요구 접수 → 분석·영향 조사 → 설계·계약 정리 → 계획·배정 → 구현 → 검증·리뷰 → 통합 검증 → 결과 반영·완료 → 후속 발견 관리까지 연결한다. 각 단계의 결과로 다음 단계를 진행하거나 필요한 단계로 돌아가 재계획한다. 결과 반영의 구체 방식과 배포 자동화 범위는 아직 정하지 않는다.

**REQ-08 모든 프로젝트의 상태 관리:** 등록된 프로젝트 전체에 대해 현재 알려진 상태와 관측되지 않는 범위를 관리한다. ‘모든 상태 관리’는 미확인 상태를 숨기거나 정상으로 추정하지 않고, 목표·프로젝트·작업·시도 수준에서 추적하는 것을 뜻한다.

| 관제 수준 | 확인할 상태 |
| --- | --- |
| 전체 목표 | 현재 단계, 조건별 달성 여부, 참여 프로젝트, 차단 사항, 다음 행동 |
| 프로젝트 | 도메인·계획 버전, 현재 작업, 기존 작업과 충돌, 연결·관측 상태 |
| 계획 작업 | 배정·선행 조건·진행·검증·대기·완료와 상태 변경 이유 |
| 실행 시도 | 실제 실행 여부, 결과, 해당 작업·계획과의 연결 |
| 판단과 발견 | 자동 판단·재검토·사람 판단 필요, 영향받는 작업, 처리 결과 |

master가 시작한 작업과 프로젝트에서 별도로 시작한 작업을 구별한다. 프로젝트의 로컬 상태는 code-agent 관측을 근거로 삼고 전체 목표의 상태는 master가 관리한다. 각 값은 근거와 마지막 관측 시점을 갖는다. 관측할 수 없는 세부 상태는 미지원·미확인으로 드러낸다.

**REQ-09 다음 행동 관리:** 상태를 표시하는 데 그치지 않고 진행 가능한 작업, 대기 이유, 재검토 필요 항목, 다음 행동을 판단해 실행한다. 프로젝트 하나의 문제가 다른 독립 작업까지 불필요하게 막지 않게 하며, 영향을 받는 작업은 의존 관계에 따라 조정한다.

수용 기준: 임의의 목표·프로젝트에 대해 “무엇을 하고 있고, 왜 그 상태이며, 무엇을 기다리고, 다음에 무엇을 할지”를 근거로 조회할 수 있어야 한다. 프로젝트별 성공만으로 전체 목표를 완료 처리하지 않는다.

## 4. 판단을 정리한 뒤 자동 실행

**REQ-10 자율 판단 우선:** 주어진 요구·근거·제약 안에서 적합한 선택지를 비교하고 자동으로 결정한다. ‘최적’은 모든 가능한 선택의 수학적 최적성 보장이 아니라, 목표 충족도·도메인 적합성·기존 계획과의 일관성·변경 영향·검증 가능성을 비교해 선택 이유를 설명할 수 있다는 뜻이다. 평가 가중치와 운영상 수치는 이번에 정하지 않는다.

**REQ-11 실행 전 판단 기록:** 계획 활성화, 업무 배정, 범위·계약 조정, 재계획, 결과 수용·완료 판정 같은 주요 행동 전에 판단 기록을 저장한다. 동일한 판단에 근거한 하위 행동은 기록을 참조할 수 있어 개별 도구 호출마다 중복 문서를 만들 필요는 없다.

판단 기록에는 판단 대상, 적용 요구, 근거와 버전, 고려한 주요 선택지, 선택과 이유, 영향 범위, 미확정 사항, 실행할 행동, 기대 결과와 검증 방법을 담는다. 내부 사고 과정 전문 대신 검토 가능한 결정 요약을 남긴다. 사람의 확인을 기다리는 것은 기본 단계가 아니다.

**REQ-12 판단과 실행의 일치:** 저장된 판단이 참조한 계획·프로젝트 상태·계약이 현재와 맞는지 검사하고 해당 판단 ID를 실제 실행에 연결한다. 기록 저장 실패, 필수 근거 누락, 상태 변경이 있으면 기존 판단으로 실행하지 않고 다시 검토한다. 판단 기록이 있다는 것만으로 권한이나 기존 승인 조건을 충족했다고 간주하지 않는다.

수용 기준: 모든 주요 실행의 직전 판단과 근거를 찾을 수 있고, 판단 후 조건이 바뀌면 재평가해야 한다. 일반적인 계획·배정·수정은 판단 기록 후 자동으로 이어져야 한다.

## 5. 모호함 재검토와 사람의 결정

**REQ-13 자동 재검토:** 모호하거나 정의되지 않은 사항은 즉시 질문으로 넘기지 않고 모호한 지점을 분리하고 추가 근거 검색, 관련 프로젝트 분석, 기존 정책·계약 대조, 대안 비교를 수행한다. 해소한 내용과 여전히 모르는 내용을 기록한다. 근거가 없는 업무 정의를 사실로 만들어 실행하지 않는다.

**REQ-14 판단 경로 구분:** 재검토 결과에 따라 아래 경로로 진행한다.

| 재검토 결과 | 행동 |
| --- | --- |
| 근거로 해소됨 | 판단을 갱신하고 자동 실행 |
| 기존 재량 안에서 영향이 제한되고 검증 가능한 선택 | 가정·선택 이유·검증 방법을 기록하고 자동 실행 |
| 정보 부족 또는 기술적 관측 실패로 아직 실행할 수 없음 | 관련 작업을 재검토·차단 상태로 관리하고 독립 작업은 진행 |
| AI가 결정할 수 없는 중대한 업무·권한 판단 | 필요한 범위만 사람에게 결정 요청 |

미해결 기술 차단은 상태로 노출하며 필요한 정보 제공·환경 복구 요청과 중대한 의사결정 요청을 구별한다. 무기한 재검토하는 동작은 허용하지 않되 구체적인 중단·재시도 정책은 운영 조건을 정할 때 상세화한다.

**REQ-15 중대한 판단 요청:** 제품 기본 원칙은 사람이 결정해야 하는 크리티컬한 사안만 올리는 것이다. 예비 분류는 업무 정책이나 핵심 책임 경계의 중대한 충돌, 허용된 권한 밖의 조치, 중대한 외부 영향이나 되돌리기 어려운 변경 등이다. 단순 구현 방식 선택이나 해소 가능한 모호함은 자동 처리한다. 이 분류는 설계 초안이며 위험 등급·금액·환경별 수치는 아직 정하지 않는다.

사람에게 올리는 항목에는 결정할 문제, 재검토한 내용, 자동 판단할 수 없는 이유, 대안과 영향, 권고안, 멈춘 작업과 계속할 수 있는 작업을 담는다. 응답 후 연결된 판단·계획을 갱신하고 다음 단계를 자동 진행한다.

현재 code-agent의 필수 승인과 이 자율 수행 목표가 충돌하는 부분은 연동 차이로 명시하고 위임 또는 승인 경로 조정을 별도 설계한다. master가 기존 승인 파일을 수정해 우회하는 방식으로 해결하지 않는다.

수용 기준: 일반적인 모호함은 재검토 후 자동 해결하고, 해결하지 못한 중요한 업무 선택은 선택지와 영향이 정리된 형태로 올린다. 근거 없는 가정, 반복 재검토, 불필요한 승인 요청을 각각 구별해 평가한다.

## 6. UI와 직접 명령의 위치

**REQ-16 관제 인터페이스:** 목표별 전체 사이클, 프로젝트별 역할·계획·상태, 자동 판단 이력, 재검토 항목, 중대한 결정 요청, 완료 근거를 확인한다. 목표 입력과 상태 조회·개입은 핵심 실행 모델을 공유한다.

**REQ-17 보조 제어:** 프로젝트·그룹 등록과 관리, 특정 프로젝트·선택한 프로젝트·그룹에 대한 직접 명령을 유지한다. 직접 명령도 진행 중 목표와 계획에 미치는 영향을 검사한다. UI 없이도 오케스트레이션 핵심 흐름을 검증할 수 있어야 한다.

그룹은 유지보수할 서비스 범위를 나타내며 여러 code-agent 프로젝트를 추가·제외할 수 있어야 한다. 그룹과 단일 프로젝트 모두 요청을 접수해 같은 계획·개발·검증·인계 절차로 수행한다. 접수 후 그룹 구성이 바뀌어도 진행 중 요청의 대상은 보존한다. 설치된 code-agent는 자동 탐색하며 사용자가 내부 실행 파일 경로를 입력하는 것을 기본 절차로 요구하지 않는다.

## 7. 현재 보류하는 범위

운영 환경·배포 토폴로지, 예산·시간·동시성·재시도 수치, 복구 정책의 세부 구현, 조직별 접근 정책, 로그 보존과 알림 정책은 지금 상세화하지 않는다. 기존 문서에 있는 관련 내용은 향후 검토할 후보로 보존한다. 보류는 해당 기능의 필요성을 부정하거나 기존 제약을 해제한다는 뜻이 아니다.

기술 스택, 개발 호스트 조합, 릴리스 단계별 세부 일정은 구현 계획에서 관리한다. 이 문서는 목표 요구사항이며 현재 구현 여부는 [구현 현황](implementation.md)과 [사용법](usage.md)에서 구분한다.
