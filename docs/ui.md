# 로컬 대시보드

기준일: 2026-10-20. 현재 제공하는 화면과 HTTP 계약을 정리한다. 설치와 기본 조작 순서는 [README](../README.md), 실행 준비와 CLI는 [사용법](usage.md)을 따른다.

## 실행과 연결

```powershell
master-agent dashboard --db <기존 DB의 절대 경로>
master-agent dashboard status --db <같은 DB 경로>
master-agent dashboard restart --db <같은 DB 경로>
master-agent dashboard stop --db <같은 DB 경로>
```

설치된 code-agent를 PATH·npm 전역 설치에서 자동 탐색하고 실제 진입점을 호출한다. 별도 빌드는 `CODE_AGENT_CLI` 또는 `--cli`로 지정한다. 기본 주소는 `http://127.0.0.1:4310`이며 `--port`로 바꾼다. 기본 조회 간격은 5초이고 `--refresh-ms`로 변경한다. `--saved`로 실행하거나 설치를 찾지 못하면 DB의 마지막 관측을 표시한다.

`dashboard` 또는 `dashboard start`는 현재 터미널에서 서버를 실행한다. `restart`는 기존 서버를 인증해 종료하고 명령을 호출한 새 프로세스에서 다시 실행한다. 같은 DB·포트·저장 관측 여부·조회 간격·명시한 CLI 경로·후보 탐색 시작 위치를 유지하며, 옵션을 주면 덮어쓴다. 서버가 종료된 상태면 마지막 설정으로 시작한다. `status`는 running·stopped·unreachable과 URL을 반환한다. `stop`은 대시보드만 종료한다.

시작·재시작 명령은 터미널을 유지해야 한다. 터미널 종료·Ctrl+C는 서버를 종료하며 자동 시작 서비스는 제공하지 않는다. 코드 변경 후 `restart`와 화면 새로고침을 수행한다. 접수된 개발 요청의 별도 실행기는 대시보드 종료와 관계없이 유지된다. 재시작 기능이 없던 버전의 서버는 최초 한 번 기존 터미널에서 Ctrl+C로 종료한 뒤 새 명령으로 시작한다.

DB 옆의 `<DB>.dashboard.json`에 마지막 설정·서버 식별자·제어 토큰을, `<DB>.dashboard.lock`에 실행 소유권을 기록한다. 제어 토큰은 화면 API로 보내지 않는다. 재시작·종료는 서버 식별자와 전용 토큰을 대조하며 저장된 PID만으로 프로세스를 종료하지 않는다. 소유 프로세스가 종료된 잠금만 회수하고, 살아 있지만 인증할 수 없는 서버는 기존 터미널에서 확인하도록 거부한다.

| 화면 증상 | 확인과 조치 |
| --- | --- |
| `대시보드 서버에 연결할 수 없습니다 (Failed to fetch)` | 같은 DB로 `dashboard status`를 확인하고 `dashboard restart`로 다시 시작한다. 출력된 URL과 브라우저 주소의 포트를 맞춘다. unreachable이면 기존 터미널의 오류를 먼저 확인한다. |
| 연결이 끊긴 뒤 카드가 계속 보임 | 마지막 수신 화면을 보존한 것이다. 서버 연결이 복구되기 전에는 최신 상태가 아니다. |
| 접속은 되지만 프로젝트가 없음 | `--db`가 기존 DB와 같은지 확인한다. 기본 DB는 명령 실행 디렉터리의 `.master-agent/master.db`다. |
| 설치를 찾지 못했다는 안내 | code-agent 설치·PATH를 확인하거나 `--cli`로 실제 진입점을 지정한다. 이 경우 대시보드 서버는 연결돼 있으며 저장된 관측을 표시한다. |
| 일부 프로젝트 조회만 실패 | 해당 카드의 미설치·시간 초과·응답 오류 사유를 확인한다. 다른 프로젝트 조회는 계속된다. |

## 프로젝트와 서비스 그룹

`그룹 만들기`는 ID·이름·유지보수 범위만 입력해 새 빈 그룹을 저장한다. 생성 창에는 소속 프로젝트 목록이나 등록 버튼을 표시하지 않는다. 저장 후 `구성 편집`에서 기존 프로젝트를 선택·제외하거나 `새 프로젝트 수동 등록`으로 기존 폴더를 추가한다. 프로젝트 목록의 `프로젝트 수동 등록`은 그룹 없이 등록한다.

등록 창 상단에서 **설치된 code-agent 프로젝트 목록**을 자동으로 불러온다. 열린 동안 대시보드 갱신 간격(기본 5초)마다 재조회하므로 실행 중 새 프로젝트에 code-agent를 설치하면 다음 조회에 나타난다. 입력 중인 이름·경로·담당 업무와 검색어를 유지한다. 이름·경로로 검색하고 선택하면 이름과 절대 경로를 채운다. 담당 업무를 입력한 뒤 저장하며 직접 입력도 가능하다. `목록 새로고침`으로 즉시 조회할 수도 있다. 이미 등록된 프로젝트는 구별해 표시하고 중복 선택을 막으며 그룹의 소속 목록에서 선택한다. master에 새로 등록한 프로젝트는 다음 상태 관측부터 포함한다.

code-agent에는 중앙 프로젝트 등록부가 없으므로 현재 작업 디렉터리·상위 위치, 등록 프로젝트·상위 위치, 소스/링크로 설치된 code-agent의 작업 위치, 사용자 홈의 IdeaProjects·projects·workspace·repos를 확인한다. 각 위치 아래 최대 두 단계에서 `.code-agent/version` 파일이 있는 폴더만 후보로 제시한다. 숨김·의존성·빌드 폴더와 하위 심볼릭 링크는 탐색하지 않는다. 최대 1,500개 디렉터리·15,000개 항목·조회 루프 2.5초 한도를 두고 제한에 닿으면 일부 결과임을 표시한다. 전체 디스크의 모든 설치를 찾는 기능은 아니므로 목록에 없는 프로젝트는 직접 입력한다. 후보 조회는 파일을 수정하거나 프로젝트를 자동 등록하지 않는다.

| 수동 등록 항목 | 입력 |
| --- | --- |
| 프로젝트 이름 | 필수 표시 이름 |
| 프로젝트 폴더 | 대시보드 서버 PC에서 접근 가능한 기존 디렉터리의 절대 경로 |
| 담당 업무 | 필수, 여러 업무는 쉼표로 구분 |
| 프로젝트 ID | 선택, 생략하면 화면에서 자동 생성 |
| 제약 사항·참고 문서/근거 식별자 | 선택, 각각 한 줄에 하나씩 입력 |

그룹 안의 신규 프로젝트는 저장 전까지 `등록 예정` 목록에만 남으며 수정·제외할 수 있다. `그룹 저장` 시 신규 프로젝트와 구성을 함께 저장한다. 경로·ID 중복, 잘못된 입력 또는 그룹 버전 충돌이면 전체 저장을 취소한다. 그룹 입력을 취소하면 신규 프로젝트도 등록하지 않는다. 그룹에서 기존 프로젝트를 제외해도 프로젝트 등록과 이전 요청의 대상은 유지된다.

등록은 폴더와 담당 업무를 카탈로그에 선언하는 단계다. 실제 경로를 정규화해 중복을 검사하며 code-agent 설치 여부는 이후 상태 조회에서 확인한다. 참고 근거를 생략하면 운영자 선언으로 기록한다. 개발 실행을 위한 정책·코드 수집, code-agent 설치·연동·권한은 [실행 전 준비](usage.md#서비스-그룹과-단일-프로젝트-요청)를 따른다.

프로젝트 카드는 경로 아래에 제어 연결 상태를 표시한다. 상태는 순회 때 읽은 토큰 없는 hello와 이 DB의 연결 기록으로 정한다: `code-agent 없음`, `PC 신뢰 필요`(PC 신뢰 버튼과 터미널 명령), `제어 연결 가능`, `제어 연결됨`(사람 응답 채널 만료일), `연동 켜짐 · 이 DB 미등록`, `다른 제어자 소유`, `터미널 연결 필요`(페어링 미지원), `연결 갱신 필요`, `관찰 연결`. 연결할 수 있으면 `제어 연결`, 만료 7일 전부터는 `다시 연결` 버튼이 나온다. code-agent에 대시보드 신뢰 기록이 없으면 `PC 신뢰` 버튼이 나온다. 신뢰 화면은 code-agent가 정한 문구(개인 키 자리·연결 범위·화면 신뢰의 한계)를 그대로 보여 주고, 확인 단어 `trust`를 그대로 입력해야 제출된다. 보인 문구가 code-agent의 지금 문구와 다르면 거부하고 최신 내용을 다시 불러온다. 신뢰 기록은 있는데 이 서버 계정에서 키를 찾지 못하면 버튼 없이 해제 뒤 다시 신뢰하도록 안내한다. 카드에는 기본 개발 호스트(요청에서 host를 고르지 않을 때)와 요청별 host 선택 지원(고를 수 있는 host)도 표시한다. 확인 화면은 경로·제어자·기본 개발 호스트와 준비 상태·요청별 host 선택 지원 여부·"연결은 승인 권한이 아님"·채널 만료 안내를 보여 주고, 확인 체크 전에는 제출할 수 없다. 기본 선택은 없다. 응답을 잃은 연결은 `연결 결과 미확인`과 같은 접수 번호로 결과를 확인하는 버튼으로 남는다. 계약은 [통신 계약](code-agent-control.md#제어-연결페어링)을 따른다.

프로젝트 카드의 `프로젝트 삭제`에서 이름·경로·제외할 그룹을 확인한 뒤 `등록 해제`를 누른다. 등록과 모든 그룹 소속을 한 트랜잭션에서 해제하고 자동 관측·새 요청·일괄 업데이트 대상에서 제외한다. 프로젝트 폴더·소스·설치된 code-agent와 이전 요청·실행·관측 이력은 보존한다. 독립 code-agent 작업을 중단하거나 설치를 제거하는 동작은 아니다.

미완료 master 목표(대기·실패·정지 포함), 실행 잠금, 프로젝트 업데이트 잠금 또는 이 프로젝트에 적용할 일괄 업데이트가 진행 중이면 409로 거부한다. 목표를 완료·취소하거나 중단된 실행을 점검한 뒤 다시 시도한다. 삭제 확인 시점의 프로젝트 버전도 대조하며 그룹 버전을 함께 갱신해 오래된 편집을 거부한다. 삭제 전 업데이트 미리보기도 무효가 된다. 이미 시작한 상태 조회는 종료될 수 있으나 삭제된 프로젝트를 다시 표시하거나 새 관측으로 저장하지 않는다.

같은 폴더는 설치 후보로 다시 선택하거나 직접 입력해 등록할 수 있다. 이전 이력과의 연결을 보존하기 위해 삭제된 ID는 재사용하지 않으며 새 ID가 필요하다. 등록 창에서 ID를 비워 두면 자동 생성한다.

그룹 카드의 `그룹 삭제`에서 이름·ID와 등록을 유지할 프로젝트를 확인한 뒤 삭제한다. 빈 그룹과 소속 프로젝트가 있는 그룹 모두 삭제할 수 있다. 그룹 목록·새 요청 대상에서 제외하며 프로젝트 등록·폴더·다른 그룹 소속은 그대로 유지한다. 이미 접수한 요청은 고정된 범위로 계속 실행하고 요청·목표 이력을 보존한다. 확인 이후 그룹 구성이 바뀌면 409로 거부하므로 최신 화면에서 다시 확인한다. 삭제된 그룹의 수정·새 요청은 거부하고 같은 ID로 다시 생성할 수 없다. CLI도 `group delete <ID> --revision <N>`으로 같은 규칙을 따른다.

프로젝트·그룹 카드의 작업 버튼은 공통 높이·간격을 사용하고 삭제 버튼은 오른쪽에 배치한다.

## 요청과 진행 관제

`그룹에 요청`, `이 프로젝트에 요청` 또는 `요청 보내기`에서 대상·선택 TASK 번호·내용·완료 조건·실행 host를 입력한다. TASK 번호는 요청 카드에 표시하고 AI 계획과 모든 프로젝트의 개발 지시에 전달한다. 이어 실행에서도 유지하며 내부 taskId·codeAgentWorkId와 구분한다. 번호의 형식과 CLI 예시는 [README](../README.md#서비스-그룹과-유지보수-요청)를 따른다.

실행 host는 `Claude`·`Codex`·`둘 다 (교차 검증)` 중에서 고른다. 고른 host가 이 요청의 code-agent 개발과 master 계획·판단을 함께 맡으며 계획·판단 담당을 따로 고르지 않는다. 둘 다를 고르면 `주 host`가 나타난다. 주 host가 개발·계획·판단을 맡고 다른 host가 교차 검증하며, 반려된 계획·판단은 실행하지 않는다. 처음 값은 대상 프로젝트의 code-agent 실행 방식이고, 그룹의 프로젝트마다 다르면 Claude 단독이다. 선택 아래에는 대상 프로젝트마다 `선택 가능`, 요청별 host 선택 미지원(code-agent 업데이트 필요), 미설치, 고른 주 host의 준비 문제를 표시한다. 연결 상태를 아직 읽지 못한 프로젝트는 접수 후 준비 점검에서 확인한다. 선택은 이 요청에만 적용하고 프로젝트의 실행 방식 설정은 바꾸지 않는다. 요청 카드에는 `host: Claude 단독`, `host: Codex 주 · Claude 교차 검증`처럼 표시한다. host 없이 접수된 요청은 `개발 host 프로젝트 설정 · 계획·판단 Claude`처럼 표시한다.

검증 계약 설정에 준비한 템플릿을 전달할 수 있다. 접수 시 대상 프로젝트·그룹 버전·서비스 범위를 고정하고, 별도 CLI 실행기가 준비 점검 후 기존 LangGraph의 계획·개발·검증·인계를 진행한다. 종료된 실행기를 자동으로 중복 실행하지 않는다.

최초 계획 전에는 표준 문서·빌드 설정의 근거를 자동 수집한다. 표준 파일이 없으면 실제 최상위 폴더 목록을 수집하며 정책·구현을 만들어내지 않는다. 설치 마커, 관리 실행 지원, 저장된 제어 연결과 실제 소유권·세대·토큰 인증을 확인한다. 그룹 요청은 대상별 부족한 준비를 함께 표시한다. 준비 문제는 `실행 준비 필요`로 대기하며 공통 요청함에서 안내·추천 재점검·보류를 제공한다. 제출하면 같은 목표·TASK로 다시 검사하고 조건이 충족된 경우에만 계획·개발로 넘어간다. 이미 실패한 `missing-knowledge` 요청도 이 안내 대상으로 표시한다.

연결이 없을 때는 토큰 없는 hello로 원인을 나눠 안내한다: PC 신뢰 필요(화면의 PC 신뢰 또는 `code-agent master trust` 명령), 제어 연결 가능, 다른 제어자 소유(정식 인계), 연동은 켜졌지만 이 DB 미등록, 페어링 미지원(기존 터미널 절차). 요청에서 고른 host가 설치되지 않았거나 준비되지 않았으면 그 사유를, code-agent가 요청별 host 선택을 지원하지 않으면 업데이트 안내를, 저장소에 커밋이 없으면 `code-agent setup baseline` 안내를 함께 표시한다. 프로젝트 설정의 host로 대신 실행하지 않는다. host 없이 접수된 요청은 code-agent가 정할 개발 호스트의 준비 문제를 표시한다. 제어 연결 가능이면 요청함에 `제어 연결 후 기존 요청 이어 실행`이 추가되고 이때는 추천·기본 선택이 없다. 이 항목을 제출하면 프로젝트별 확인 화면이 먼저 열리고, 모든 연결이 등록된 뒤에만 같은 요청을 재점검·재개한다.

최초 설치·권한 부여는 자동 승인하지 않는다. 요청함의 프로젝트별 지침과 현재 DB 경로로 연결한 뒤 `준비 다시 확인 · 기존 요청 재개`를 제출한다. 개발 호스트는 code-agent의 실행 선택과 등록 설정을 따르며, 호스트별 권한·신뢰는 code-agent가 검사한다. Codex 프로젝트에 Claude 설치를 일괄 요구하지 않는다. 목표 작업 표에는 실행에서 확인된 호스트를 표시한다. 프로젝트 카드에는 작업이 없어도 해당 요청의 실패·준비 사유를 표시하고, 목표 진행도 실패를 계속 계획 중으로 표시하지 않는다. 계획 후 독립 검증 계약이 없으면 요청함에 등록 명령을 안내한다. 계약을 임의 생성하지 않으며 등록 후 같은 요청을 재개한다. 실행 중 업무 질문도 공통 요청함에서 처리한다.

| --- | --- |
| 전체 요약 | 등록 프로젝트, 진행 중 목표, 판단·점검 필요, 조회 오류·오래된 관측 수 |
| 서비스 그룹 | 이름·유지보수 범위·소속 프로젝트·편집·요청 버튼 |
| 보낸 요청 | 접수 당시 대상·TASK 번호·목표·실행 상태·대기/오류 사유·이어 실행 |

| 목표별 진행 | 작업별 실행·승인 처리·사람 응답·장애 상태, 최근 12개 이벤트; 모의 실행 별도 표시 |

목표가 없는 독립 code-agent 작업도 등록 프로젝트라면 조회한다. 상태는 `status --json`, 연결된 프로젝트의 이벤트는 `master call events`, 질문·승인은 공통 요청함 API로 읽으며 모든 브라우저가 수집 결과를 공유한다. 최대 4개 프로젝트씩 조회하고 읽기 호출당 5초로 제한하며, 전체 조회 완료 후 다음 조회를 예약한다. 마지막 상태 관측이 30초 또는 조회 간격의 3배 중 큰 값을 넘으면 오래된 상태로 표시한다. 조회 실패 뒤 보존한 이전 작업도 구별한다. 상태 조회만으로 OS 프로세스 생존이나 제어권의 현재 유효성을 확정하지 않는다.

### 단계별 이력 수집과 조회

1. 등록 프로젝트의 상태 변화가 생기면 이전/현재 단계·담당 작업·브랜치·실행 시도·대기 사유·검증 결과를 DB에 누적한다. 관측 시각이나 stateVersion만 바뀌면 추가하지 않는다. 조회 실패·복구는 구별하며 작업 없음이나 브랜치 전환을 성공으로 해석하지 않는다.
2. 제어 연결이 있는 프로젝트는 실행 호스트와 **별도의 이벤트 커서**로 최초 보존 이벤트부터 이어 읽는다. 조회당 최대 200건·5페이지이며 나머지는 다음 순회에서 수집한다. 프로젝트·원장 ID·순번으로 중복을 차단한다. 원장 교체·보존 구간 누락은 명시적으로 기록하고 남아 있는 첫 이벤트부터 재개한다. 조회 실패는 기존 이력과 커서를 보존하며 타임라인에 오류를 표시한다.
3. 질문·승인은 발행 상태와 적용·재개 상태 변화를 기록한다. 전문·답변·로컬 보류 명령 이력과 제출은 공통 요청함에서 확인한다. 타임라인은 임의 원본 이벤트, 서명 키, 모델 입력을 노출하지 않는다.
4. 이력은 **최신 수집 순**으로 기본 50건씩 표시한다. 실제 이벤트 시각과 수집 시각을 구분하며 `이전 이력`으로 과거 기록을 조회한다. 과거 페이지는 자동 갱신으로 이동하지 않고 `최신 이력`으로 돌아온다. TASK 검색은 부분 일치이며 작업·실행·시도 ID도 검색한다.
5. 그룹은 수집 당시 소속을 보존한다. 정확한 프로젝트·실행 연결이 있는 master 작업은 요청 당시 그룹 범위와 TASK를 사용한다. 현재 작업 ID가 같다는 이유만으로 다른 실행에 연결하지 않는다. 작업 식별자가 없는 이벤트는 프로젝트 범위로 표시한다. 등록 해제된 프로젝트의 이력은 DB에 보존하고 현재 관제 조회에서 제외한다.

제어 연결이 없으면 상태 관측 이력만 제공한다. 관측 사이에 끝난 단계는 놓칠 수 있고, 독립 실행이 code-agent 이벤트를 발행하지 않은 경우 상태 변화만 남는다. 기능 도입 전의 관측은 당시 최신값만 있었으므로 과거 타임라인을 만들어내지 않는다. `--saved`는 외부 이력을 새로 수집하지 않는다. 모든 단계의 시작·완료를 보장하는 계약과 산출물 전문·실시간 로그는 후속 범위다.

## code-agent 일괄 업데이트

1. 기본 방식인 `원격 최신 버전 받아 적용`에서 `전체 프로젝트 업데이트 확인`을 누른다. 설치된 code-agent Git 소스의 브랜치·upstream과 모든 등록 프로젝트의 버전·적용 가능 여부를 조회한다. 미리보기는 로컬 조회만 수행한다. 미설치, 버전 조회 오류, 작업·승인 대기, master 실행 잠금이 있으면 해당 프로젝트는 건너뛴다.
2. 원격 브랜치와 대상 목록을 확인한 뒤 `원격 받기·빌드·검증 후 일괄 적용`을 누른다. 별도 사본을 만들고 `git pull --ff-only`로 추적 브랜치의 변경을 받는다. 로컬 전용 커밋·분기 때문에 원격 HEAD와 같아질 수 없으면 중단한다. `npm ci --include=dev`(prepare 등 설치 스크립트 포함), `npm run build`, `npm test`가 모두 성공해야 적용 단계로 넘어간다. 준비 중에는 기존 프로젝트를 바꾸지 않으며 원본 소스의 미커밋 변경은 포함하거나 덮어쓰지 않는다.
3. 빌드 결과를 공개 명령 `update --templates-only`가 인식하는 패키지 사본으로 제공하고 code-agent 릴리스 저장소에 등록·적용한다. 중간 빌드 대신 검증된 동일 패키지를 순차 적용하고 프로젝트별 목표 릴리스 일치를 다시 검사한다. 단계별 진행·출력, 받은 커밋, 성공·건너뜀·실패·수동 확인 필요 결과를 표시한다. 사용자 수정 템플릿·충돌·호스트 재시작은 code-agent 안내를 따르며 프로젝트를 자동 커밋하지 않는다.

Git 소스 설치와 단일 원격 추적 브랜치가 필요하다. detached HEAD·upstream 누락·접근 실패는 사유를 표시하며 다른 저장소를 추정하지 않는다. npm·단일 실행 파일 설치는 기존 배포 방식으로 갱신하거나 `현재 설치본만 적용`을 선택한다. 현재 설치본 방식은 원격 다운로드·빌드 없이 npm 패키지는 `update --templates-only`, 소스/번들은 `update --bundled`로 적용한다. 후자는 기존 릴리스 고정을 해제하므로 미리보기에 표시한다.

**브랜치별 작업 조회와 업데이트 보호는 별도다.** 프로젝트 카드는 `status --json`으로 현재 브랜치의 작업을 조회한다. 업데이트의 건너뜀 사유는 `version --json`의 `project.busy`를 사용한다. 2026-10-19 확인한 code-agent는 작업 조회에 `currentCursor`, 버전 변경 검사에 `allCursors`를 사용해 다른 브랜치의 미완료 작업도 보호한다. 따라서 현재 브랜치가 `no-work`여도 `진행 중인 작업 … (…, 다른 브랜치)`로 건너뛸 수 있다. 이 사유는 저장된 미완료 상태이며 OS 프로세스 실행을 증명하지 않는다. 해당 프로젝트에서 두 공개 조회 명령을 비교하고 표시된 작업의 완료·중단 여부를 확인한다. master-agent가 작업 기록을 삭제하거나 code-agent의 적용 거부를 우회하지 않는다.

빌드 사본은 DB 디렉터리의 `code-agent-builds/<고유 ID>/node_modules/code-agent`에 보존한다. 원본 Git 메타데이터도 같은 고유 디렉터리에 별도로 보관한다. 실행 중인 버전이나 훅이 참조할 수 있으므로 자동 삭제·덮어쓰기하지 않는다. 실패·중단 사본을 다음 실행에서 재사용하지 않는다. 원격 URL과 인증 정보는 화면과 DB 진행 기록에 노출하지 않는다. 인증 입력은 비대화식이며 실패 시 서버 실행 계정의 Git 인증·접근 권한을 확인한다.

미리보기는 15분간 유효하며 설치 해시·프로젝트 버전과 소스 HEAD·브랜치·upstream 설정을 대조한다. 실제 원격 커밋은 실행 시 pull로 확정하고 결과에 기록한다. 빌드 후 패키지 해시를 고정하며 적용 중 변경되면 남은 적용을 중단한다. 같은 미리보기 재전송은 기존 실행을 반환한다. 개발 잠금과 업데이트 잠금을 상호 배제하고 code-agent가 적용 직전 자신의 작업·승인 상태를 다시 검사한다. 버전 조회 15초, 프로젝트 적용 120초, pull 3분, 의존성 설치·빌드 각각 15분, 테스트 20분의 한도를 둔다.

브라우저를 닫아도 실행은 서버에서 계속된다. 정상 서버 종료는 현재 준비·적용 단계가 끝날 때까지 기다리고 나머지는 취소한다. 오래 걸리면 `dashboard restart`의 종료 대기 한도를 넘을 수 있으므로 현재 서버 종료 후 다시 시작한다. 서버 강제 종료·시간 초과는 성공 처리하거나 자동 재실행하지 않는다. 종료가 불명확한 프로젝트의 개발 잠금은 유지하며, 결과의 `종료·유휴 상태 확인 후 잠금 해제`로 관련 프로세스 종료·code-agent 유휴·runtime 잠금 부재를 확인한 뒤 해제한다. runtime 잠금이나 작업이 남아 있으면 터미널에서 먼저 점검한다. 해제는 적용 성공을 뜻하지 않으며 다시 조회·적용해야 한다. 최근 5개 실행을 화면에 표시하고 전체 기록은 DB에 보존한다.

## 로컬 HTTP 계약

| 경로 | 역할 |
| --- | --- |
| `GET /api/overview` | 프로젝트·그룹·요청·목표·업데이트·공통 요청함과 현재 화면의 요청 토큰 |
| `GET /api/history` | `projectId`, `groupId`, `task` 필터, `before` 수집 순번 커서, `limit` 1~100(기본 50). `items`, `nextBefore`, 프로젝트별 이벤트 수집 상태를 반환 |
| `POST /api/interactions/respond` | 요청 ID·revision·contentHash·context·commandId와 명시적 답변/보류/재열기/승인. 상세는 아래 공통 요청함 계약 |
| `POST /api/interactions/retry` | `{commandId}`로 미확인 전송을 같은 영속 envelope로 재전송하거나 중단된 master 재개를 대조. 임의 명령·경로·서명 키 입력은 받지 않음 |
| `POST /api/project-candidates` | 알려진 작업 위치의 설치 프로젝트·등록 여부 조회. 요청 본문으로 탐색 경로를 지정하지 않으며 동시 조회는 공유 |
| `POST /api/projects` | `{project}`로 수동 등록 |
| `POST /api/projects/delete` | `{id, revision}`으로 등록 해제·그룹 제외. 폴더와 실행 이력 보존, 미완료 목표·실행/업데이트 사용 중이면 409 |
| `POST /api/trust/preview` | code-agent의 PC 신뢰 확인 문구·`shownHash`·신뢰 가능 여부. 아무것도 쓰지 않음. code-agent가 화면 신뢰를 모르면 터미널 명령 안내 |
| `POST /api/trust` | `{shownHash, word: "trust"}`로 사람이 확인한 PC 신뢰 등록. 확인 단어·해시 형식 오류 400, 보인 내용과 다름 409, 이미 신뢰 400. 응답은 지문·등록 시각만(개인 키·경로 없음) |
| `POST /api/projects/pair/preview` | `{projectId}`로 제어 연결 확인 화면 내용·연결 상태·`shownHash` 생성. 토큰 없는 hello만 읽음 |
| `POST /api/projects/pair` | `{projectId, projectRevision, commandId, confirmed: true, shownHash}`로 사람이 확인한 연결 실행. 확인 체크 없음 400, 내용·버전 변경 409. 응답에 토큰 파일 경로를 넣지 않음 |
| `POST /api/projects/pair/retry` | `{commandId}`로 결과 미확인 연결을 같은 서명으로 재전송하거나 DB 등록 실패를 다시 등록 |
| `POST /api/groups` | `{group, revision, newProjects?}`로 그룹과 신규 프로젝트를 원자적으로 저장. 신규 프로젝트는 요청당 최대 100개 |
| `POST /api/groups/delete` | `{id, revision}`으로 그룹 삭제. 소속 프로젝트·기존 요청 유지, 버전 불일치 409, 삭제된 그룹의 수정·새 요청 404 |
| `POST /api/requests` | 그룹 또는 단일 프로젝트 요청 접수·실행. 선택 필드 `taskNumber`, 실행 host `host: {mode, main?}`(mode는 claude·codex·both, `provider`와 함께 쓰지 않는다) 지원 |
| `POST /api/requests/continue` | 요청 ID·버전을 대조하고 같은 목표 이어 실행 |
| `POST /api/updates/preview` | `{mode?: "remote" | "installed"}`로 미리보기 생성. 기본 remote는 설치 소스의 upstream 확인, installed는 현재 설치본 적용 |
| `POST /api/updates/apply` | `{id}`로 서버가 생성한 미리보기 실행. 임의 경로·명령은 받지 않음 |
| `POST /api/updates/recover` | `{id: 프로젝트ID}`로 중단된 업데이트의 종료·유휴 상태를 점검하고 잠금 해제 |

서버는 loopback에만 바인딩하고 Host·Origin을 검사한다. 후보 조회를 포함한 POST는 정확한 Origin·화면 토큰·JSON 형식·256KiB 한도를 대조한다. code-agent 제어 토큰과 원본 모델 입력은 노출하지 않는다. 프로젝트 잠금·검증 계약·grant·승인 규칙은 기존 실행 경로와 같다.

CLI 전용 `POST /api/dashboard-control`은 별도 제어 토큰과 서버 ID로 status·stop을 처리한다. 화면 토큰으로는 호출할 수 없다. restart는 이 종료 경로를 확인한 뒤 새 CLI 프로세스가 서버를 시작하는 동작이다.

## 공통 요청함

전체·발행 주체·프로젝트·그룹·작업/TASK 검색·단계·상태로 필터링한다. 질문의 첫 관측/발행 시각부터 대기 시간을 표시하며 새 요청 표시는 현재 페이지에서 열어본 여부다. 그룹 요청은 접수 당시 그룹·프로젝트 범위를 보존한다. master 목표가 없는 독립 code-agent 설정/운영 질문도 표시한다.

master 분석의 추천은 실제 선택지 문구와 정확히 일치할 때만 기본 선택한다. code-agent는 발행자의 추천 ID·이유·근거·옵션별 결과를 사용하고, 다중 선택 기본값은 명시된 `defaultOptionIds`만 따른다. 직접 입력·옵션별 입력 조건을 표시하며 폼을 열거나 추천을 선택한 것만으로 제출하지 않는다. 폴링 중 입력을 유지하고 탭의 sessionStorage에 초안을 보존한다. 질문 변경 시 이전 초안을 자동 적용하지 않고 최신 질문을 다시 열게 한다.

승인은 별도 창에서 전문과 변경 후보를 보여 준다. 전문 확인 체크·승인/수정 요청·각 후보의 적용/유지는 기본 선택하지 않는다. 서버는 원래 요청의 최신 버전·해시·문맥을 다시 읽고, 화면 Origin·토큰 검사 후에만 별도 사람 채널 키로 서명한다. AI 위임 grant나 훅 관찰 기록으로 대체하지 않는다. 최초 연결과 지원 빌드는 [README](../README.md)와 [연동 계약](dashboard-interactions.md)을 따른다.

code-agent의 보류는 원래 요청을 deferred로 만들며 다시 열기를 명시적으로 제출해야 답할 수 있다. master/구형 code-agent 표시의 보류는 master 목록에만 기록하고 원래 작업을 바꾸지 않는다. 답변 전송함에는 commandId·정확한 서명 요청을 먼저 저장하고 통신 실패는 `수신 여부 미확인`으로 보존한다. 이력의 재시도 버튼은 같은 명령을 재전송한다. 수신은 소비·적용·재개·업무 완료를 뜻하지 않는다. 적용 오류와 재개 차단은 원래 결과로 표시한다.

master 분석은 모든 질문에 답한 뒤 기존 target-request를 재분석한다. 복구 답은 기존 시도·검증 실행에 결속하고 기존 Recovery 처리기로 파일·상태·권한을 다시 검사한다. CLI로 만든 목표는 답을 저장한 뒤 기존 CLI 명령으로 이어간다. code-agent 세션 재개는 해당 API의 continuation과 원래 supervisor에 맡기며 대시보드가 새 개발 작업을 만들지 않는다. 응답 전송·적용이 미확인인 프로젝트의 등록 해제·업데이트는 막는다.

제어 연결이나 사람 키가 없으면 불가 이유를 표시한다. 구형 빌드는 `questions`/`consents` 또는 상태 요약으로 관측하고 제출은 제공하지 않는다. 조회 실패는 마지막 기록을 보존한다. `--saved`에서는 외부 요청을 새로 조회하지 않는다.
