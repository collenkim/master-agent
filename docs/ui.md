# master-agent 대시보드와 UI 계획

## 현재 구현: 로컬 관제·서비스 그룹·요청 실행

`master-agent dashboard --db <DB 경로>`로 실행합니다. 설치된 code-agent를 PATH·npm 전역 설치에서 자동 탐색하고 셸 래퍼 대신 실제 진입점을 호출합니다. 기본 주소는 `http://127.0.0.1:4310`이며 `--port`로 변경합니다. 기본 조회 간격은 5초이고 `--refresh-ms`로 변경합니다. `--saved`로 실행하거나 설치를 찾지 못하면 DB의 마지막 관측을 표시합니다. 별도 빌드는 `CODE_AGENT_CLI` 또는 `--cli`로 지정합니다. 설치·DB 경로 선택은 [README](../README.md)를 따릅니다.

등록 프로젝트 전체의 현재 작업·단계·승인·답변 대기·답변 검증 대기·리뷰 지적·임대·관측 시각을 표시합니다. 목표가 없는 독립 code-agent 작업도 포함합니다. 이름·경로·작업 검색과 판단 필요·조회 오류 필터를 제공합니다. 목표별로 master의 실행·승인 처리·사람 응답·장애 상태와 최근 12개 이벤트를 확인합니다. 모의 실행은 실제 실행과 구분합니다.

자동 관측은 `status --json`만 호출하며 전체 브라우저가 같은 조회 결과를 공유합니다. 프로젝트 조회는 최대 4개씩 실행하고 각 호출을 5초로 제한합니다. 한 번의 전체 조회가 끝난 뒤 다음 조회를 예약하므로 느린 프로젝트로 중복 조회가 쌓이지 않습니다. 개별 실패에도 다른 프로젝트를 표시합니다. 마지막 상태의 관측 시각이 30초 또는 조회 간격의 3배 중 큰 값을 넘으면 오래된 관측으로 표시하며, 조회 실패 뒤 보존한 이전 작업도 명시합니다. 상태 조회만으로 OS 프로세스 생존이나 제어권의 현재 유효성을 확정하지 않습니다.

서비스 그룹에는 이름·유지보수 범위·소속 프로젝트를 저장합니다. 그룹 생성과 구성 편집에서 등록된 프로젝트를 추가·제외합니다. 저장은 기대 버전을 대조해 다른 화면의 변경을 덮지 않습니다. 그룹 요청은 접수 시 대상·버전·설명을 고정하므로 이후 구성 변경은 새 요청부터 적용됩니다.

그룹 카드의 `그룹에 요청`, 프로젝트 카드의 `이 프로젝트에 요청` 또는 `요청 보내기`에서 대상·내용·완료 조건·계획 provider를 선택합니다. 고급 설정에서 준비한 검증 템플릿을 전달할 수 있습니다. 접수는 실제 목표와 영속 요청 기록을 함께 만들고 별도 CLI 실행기가 기존 LangGraph를 진행합니다. 브라우저·대시보드를 닫아도 실행기는 유지됩니다. 실행 상태·대기·오류는 `보낸 요청`에서 확인하고 설정·답변 보완 후 같은 목표를 이어 실행합니다. 실행기가 종료됐으면 자동 중복 실행하지 않고 중단 상태를 표시합니다.

HTTP는 loopback에만 바인딩합니다. `GET /api/overview`는 요약과 현재 화면의 요청 토큰을 제공하며, 변경 POST는 정확한 Origin·화면 토큰·JSON 형식과 256KiB 제한을 검사합니다. `/api/groups`, `/api/requests`, `/api/requests/continue`만 변경 경로로 제공합니다. code-agent 제어 토큰·원본 모델 입력은 노출하지 않습니다. 요청을 보내도 기존 프로젝트 잠금·검증 계약·grant·승인 규칙은 그대로 적용됩니다. 실행 중지·승인·사람 답 전달은 기존 CLI를 사용합니다. 미등록 디렉터리 탐색과 여러 PC 통합은 후속 범위입니다.

## 후속 제품 화면 설계

아래 구성은 목표 입력과 실행 제어까지 확장하기 위한 설계이며 현재 구현을 뜻하지 않습니다.

UI는 AI 오케스트레이션의 목표·계획·진행·근거를 관찰하고 필요한 판단을 전달하는 창입니다. 기본 화면은 Mission 작업 공간입니다. 사용자가 목표를 입력하면 master가 관련 프로젝트와 실행 계획을 제안합니다. 프로젝트 목록과 직접 명령은 보조 화면으로 제공합니다.

기능 범위는 [요구사항 문서](requirements.md)를 따릅니다. 운영 조건 입력과 표시는 설계 후보이며 이번 상세화에서 확정하지 않습니다.

## 1. 화면 구성

```text
┌───────────────────────────────────────────────────────────────────────┐
│ master-agent          목표·프로젝트 검색          연결 상태  새 목표  │
├──────────────┬────────────────────────────────────────────────────────┤
│ 목표 작업    │ 목표: 출고 전 주문 취소와 환불·쿠폰 복구              │
│ 판단 필요 3  │ 상태: 실행 중 · 계획 v2 · 필수 완료 조건 2/5 충족     │
│ 프로젝트     │                                                        │
│ 그룹         │ 계약 정리 → 주문 구현 ─┐                             │
│ 실행 이력    │           → 결제 구현 ─┼→ 통합 검증 → 완료 판정      │
│ 설정         │           → 쿠폰 구현 ─┘                             │
│              │                                                        │
│              │ 현재 판단: 환불 확정 이벤트 계약 변경                │
│              │ [계획 변경 비교] [질문과 근거] [일시 정지]            │
├──────────────┴────────────────────────────────────────────────────────┤
│ 실행 중 2 · 응답 필요 1 · 연결 오류 1                                 │
└───────────────────────────────────────────────────────────────────────┘
```

사이드바는 목표 작업, 판단 필요, 프로젝트, 그룹, 실행 이력, 설정으로 구성합니다. 목표 작업 목록에는 목표명, 현재 단계, 완료 조건 충족 수, 차단 이유, 마지막 활동을 표시합니다. 프로젝트별 성공 수는 상세 지표로 두고 목표 달성 여부와 구분합니다.

넓은 화면에서는 목록과 상세 패널을 나란히 표시합니다. 좁은 화면에서는 상세와 명령 작성 화면을 전체 페이지로 열고 선택 상태를 유지합니다. 상태는 색과 텍스트를 함께 사용하고, 표·대상 선택·질문 응답을 키보드로 조작할 수 있게 합니다.

### 목표 입력과 분석

새 목표 화면에서 자연어 목표와 참고 자료를 입력합니다. 허용 프로젝트·그룹, 제외 범위, 완료 조건, 시간·비용 한도는 추가 설정으로 받습니다. 프로젝트를 직접 지정하지 않으면 등록된 허용 범위에서 master가 관련 대상을 찾습니다. 필수 작업 예산은 실행 정책의 기본값을 적용하고 화면에서 확인할 수 있게 합니다.

분석 결과는 목표 해석, 완료 조건, 관련 프로젝트와 선택 근거, 미확정 질문으로 나눠 보여 줍니다. 근거 문서와 버전을 열 수 있게 하고, 후보·확인된 사실·미확정 사항을 구별합니다. 이미 허용된 범위 안의 작업은 정책에 따라 이어가고 필요한 판단이 있을 때만 입력을 요청합니다.

### 목표 상세와 계획

목표 상세는 `개요 / 계획 / 진행 / 판단 / 검증 근거 / 이력` 탭으로 구성합니다. 계획 탭에서는 프로젝트별 역할, 작업 의존 관계, 산출물과 검증 노드를 표시합니다. 그래프와 동등한 정보를 제공하는 목록 보기도 둡니다.

재계획 시 이전·새 계획의 차이, 변경 이유, 영향받는 작업, 다시 검증해야 할 증거를 보여 줍니다. 사용자의 계획 수정은 변경 제안으로 접수하고 새 버전 검증 후 적용합니다. 사용자가 지시를 보내는 것과 즉시 실행 중인 작업을 변경하는 것을 구별합니다.

진행 탭에는 AI의 다음 행동과 기록된 판단 근거 요약, 실행 중 작업, 대기 이유, 예산 사용량을 표시합니다. 내부 사고 과정 대신 참조한 근거·선택한 행동·검증 결과를 제공합니다.

자동 판단 이력에는 실행 전 정리한 선택·근거·영향·검증 방법과 실제 실행을 연결합니다. 재검토 중인 모호함, 정보 부족으로 막힌 항목, 사람의 결정이 필요한 중대한 사안을 구별합니다. 자동 판단은 별도 확인 버튼을 누르지 않아도 진행하며 판단함은 사람이 결정해야 하는 항목에 집중합니다.

검증 근거 탭은 완료 조건마다 프로젝트별 증거와 통합 검증 결과를 연결합니다. 성공·실패·미검증·오래된 증거를 구분하고, 통합 환경이 없어 검증하지 못했다면 목표 완료로 표시하지 않습니다.

### 수동 개입

목표별로 추가 정보 전달, 변경 요청, 새 배정 일시 정지, 재개, 취소를 제공합니다. 실패 재시도는 현재 계획·입력·예산을 재검사하는 동일 경로를 사용합니다. 일시 정지 후에도 진행 중인 프로세스는 별도 표시하고, 취소 완료는 실제 종료 확인 후 표시합니다.

직접 프로젝트 명령이 실행 중 목표에 영향을 주면 해당 Mission과의 충돌 또는 재평가 대상을 보여 줍니다. 보조 명령도 동일한 실행 잠금·승인·증거 규칙을 따릅니다.

## 2. 프로젝트 목록과 등록

목록의 기본 열은 선택, 프로젝트 이름, 그룹, 현재 작업, 작업 상태, 연결 상태, 마지막 조회 시각입니다. 설치 버전·호스트·경로는 상세 패널에서 제공합니다. 연결 오류를 작업 실패와 같은 표시로 합치지 않습니다.

등록 창에서는 표시 이름과 로컬 경로를 입력합니다. 서버가 실제 경로, 저장소 루트, code-agent 설치 마커, 호스트 정보와 JSON 조회 가능 여부를 검사합니다. 성공하면 등록하고 실패하면 원인을 보여 줍니다. 일부 정보만 확인할 수 있을 때는 미확인 상태로 등록할 수 있지만 실행 기능은 활성화하지 않습니다.

후보 탐색은 사용자가 지정한 폴더와 탐색 깊이 안에서만 수행합니다. 발견한 프로젝트를 자동 등록하지 않고 체크박스로 선택하게 합니다. 중복 경로는 기존 등록 이름을 표시합니다.

프로젝트 목록의 빈 화면에는 `프로젝트 등록`과 `폴더에서 찾기`를 제공합니다. 목표는 초안으로 먼저 작성할 수 있으며 실행 후보가 없으면 프로젝트 연결을 안내합니다. 예시 데이터는 실제 프로젝트 목록에 섞지 않습니다.

## 3. 그룹 화면

그룹 목록에는 이름, 설명, 프로젝트 수, 진행 중 작업 수, 응답 필요 수를 표시합니다. 그룹 상세에서는 구성원 목록과 그룹 실행 이력을 함께 확인합니다.

그룹 편집에서 프로젝트를 검색해 추가·제외합니다. 프로젝트가 다른 그룹에도 속해 있으면 해당 소속을 표시합니다. `그룹 명령` 버튼은 그룹 구성원을 선택한 명령 작성 화면을 엽니다. 실행 중에 그룹을 편집하더라도 기존 실행의 대상은 바뀌지 않는다는 설명을 편집 결과에 표시합니다.

## 4. 보조 기능인 직접 명령 화면

개별·선택·그룹 명령은 운영 점검과 구체적인 작업 지시에 사용합니다. 개발 명령은 Mission으로 연결되고, 여러 프로젝트의 역할·순서 판단이 필요하면 오케스트레이터가 계획합니다. 아래 독립 실행 예시는 단순 배정에 해당합니다.

```text
새 명령

대상 범위    ( ) 프로젝트 하나  ( ) 선택한 프로젝트  (●) 그룹
그룹         [커머스 ▾]
실제 대상    ☑ 주문 API  ☑ 관리자 UI  ☐ 주문 배치
             3개 중 2개 실행 · 제외 1개

명령 종류    [개발 요청 ▾]
공통 지시    [주문 취소 사유 입력 기능을 추가해줘.              ]

프로젝트별 지시
  주문 API    추가: 사유 저장과 조회 API를 구현
  관리자 UI   추가: 취소 화면에 입력 필드를 추가

실행 방식    [독립 실행 ▾]       동시 실행 수 [2]
실행 호스트  [프로젝트 설정 사용 ▾]

                              [초안 저장] [실행 내용 확인]
```

프로젝트 하나를 선택한 경우에도 같은 화면을 사용합니다. 공통 지시 없이 프로젝트마다 서로 다른 명령을 작성하는 것도 허용하며, 모든 대상의 최종 지시는 비어 있지 않아야 합니다.

명령 종류별 UI는 구분합니다. 상태 조회·설치 점검은 고정 동작을 선택하고, 개발 요청은 자연어 지시를 입력합니다. 재개는 해당 프로젝트의 현재 작업에서 시작하며 기대 상태 버전을 묶습니다. 자유로운 셸 명령 입력은 초기 제품 범위에 포함하지 않습니다.

실행 내용 확인에서는 실제 대상, 제외 사유, 프로젝트별 최종 지시, 호스트, 기존 작업과의 충돌, 실행 순서를 보여 줍니다. 이 확인은 명령 배정 범위를 확정하는 단계이며 code-agent의 요구사항·계획 승인 절차를 대신하지 않습니다.

사용 가능한 기능만 선택할 수 있습니다. 예를 들어 상태 조회만 연결된 프로젝트는 개발 요청을 선택했을 때 `개발 호스트 연결 필요`로 표시합니다. 단순히 접수 기록이 생성됐다는 이유로 실행 중이라고 표시하지 않습니다.

## 5. 보조 명령의 실행 내역과 상세

실행 내역은 명령 이름, 요청 범위, 대상 수, 성공·실패·응답 필요 수, 요청 시각으로 구성합니다. 그룹명뿐 아니라 실제 대상 수를 표시하고, 당시 구성원을 열어 볼 수 있게 합니다.

```text
주문 취소 사유 추가                      일부 실패 · 성공 1 / 실패 1
대상: 커머스 그룹 중 2개                 요청 시각: 14:30

프로젝트       배정 상태       로컬 단계       결과
주문 API       완료            검증 완료       변경·검증 근거 보기
관리자 UI      실패            테스트          오류 보기 / 재시도

[개요] [프로젝트별 결과] [로그] [질문과 승인] [변경·검증 근거]

선택한 프로젝트: 관리자 UI
시도 1 · 시작 14:31 · 종료 14:36
실패 원인과 마지막 상태 관측 시각

                              [실패한 대상 선택] [선택 대상 재시도]
```

실시간 로그와 상태 이벤트를 분리해 표시합니다. 재연결 시 마지막 이벤트 이후를 이어 받고 중복 이벤트를 제거합니다. 프로젝트별 로그 선택과 자동 스크롤 일시 정지를 제공합니다.

master 실행 상태, code-agent 개발 단계, 러너 프로세스 상태를 각각 표시합니다. 예를 들어 `master: 확인 필요 / code-agent: 테스트 / 프로세스: 관측 불가`처럼 설명할 수 있어야 합니다.

취소는 개별 프로젝트 또는 전체 실행을 대상으로 요청할 수 있습니다. 부분 취소와 전체 취소는 이미 완료된 결과를 유지합니다. 재시도 화면은 실패한 대상만 기본 선택하고 새 시도가 생긴다는 점을 표시합니다.

## 6. 프로젝트 상세

헤더에는 이름, 경로, 그룹, 연결 상태와 `명령 실행` 버튼을 배치합니다. 탭은 개요, 현재 작업, 실행 이력, 지식·발견, 설정으로 구성합니다. 지식·발견 탭은 조회 연결이 구현된 시점에 활성화합니다.

개요와 현재 작업에서 도메인 책임, 구현 가능한 범위·제약, 현재 프로젝트 계획, master가 배정한 역할·이유·산출물과 다른 프로젝트와의 연계를 확인할 수 있게 합니다.

현재 작업에서는 master가 시작했는지 외부 호스트가 시작했는지 표시합니다. 외부 작업은 조회할 수 있지만 실행 소유권 확인 없이 취소·재개하지 않습니다. 작업이 없어도 설치 상태와 마지막 관측 시각을 보여 줍니다.

설정에서는 표시 이름, 그룹, 실행 위치, code-agent 실행 파일, 개발 호스트를 관리합니다. 경로 변경 시 기존 프로젝트와 일치하는지 재검사합니다. 프로젝트 보관은 이력을 유지합니다.

## 7. 응답 필요 화면

목표 해석·계획 변경·범위 확대에 대한 판단과 프로젝트별 code-agent 질문·승인을 모읍니다. 종류, Mission, 프로젝트, 발생 시각과 차단 중인 작업을 표시합니다. 한 항목을 열면 질문 원문, 선택지, 판단 근거, 현재 계획·상태 버전과 응답의 영향 범위를 보여 줍니다.

초기 연결에서는 기존 호스트에서 응답해야 하는 항목을 `호스트에서 확인 필요`로 안내합니다. master UI의 응답을 code-agent의 기존 검증 경로로 전달할 수 있게 된 뒤 응답 입력을 활성화합니다. 이전 상태에 대한 응답은 거부하고 변경된 질문과 계획을 다시 표시합니다.

## 8. 오류와 비어 있는 상태

분석에는 `결과 적용 취소` 동작과 interrupted 이력을 제공한다. AI 프로세스 종료와 혼동하지 않도록 모델 호출은 반환·시간 제한까지 남을 수 있음을 표시한다. 검증 중단 상세에는 명령별 반환 기록과 누락·미반환·변조·입력 변경 사유를 표시한다. 대조 통과는 완료가 아닌 `새 독립 검증 대기`로 보여 준다. 관련 CLI는 [분석·검증 중단 처리](interruption.md)를 따른다.

완료 증거에는 `로컬 파일 검증`과 `로컬 커밋·동의 기록 대조`를 구분한다. 반영 기록에는 커밋·영수증 출처·후검증 결과를 표시하며 push·배포 완료로 표시하지 않는다. 미확인 시도에는 현재 호출 반환 기록의 유무와 복구 차단 이유를 보여 주고, 복구 후에는 `독립 검증 대기`로 표시한다. CLI 계약은 [반영 기록·관측 복구](delivery-reconciliation.md)에 정리했다.

재계획 이력은 `mission show`의 `replans`와 분석 기록을 연결한다. 이전 실패 시도는 성공과 구별해 `재계획으로 인계됨`으로 표시하고, 보존한 변경·외부 종료 관측·새 계획 버전·검증 계약 재등록 필요를 보여 준다. 인계 후 분석 실패는 기존 계획 재실행 버튼 대신 재분석 안내를 제공한다.

목표 상세의 복구 이력에는 실패한 검증 명령과 진단, 현재 코드 근거, AI 원인 분석·대안·수정 단계, 자동 실행 허용 여부와 차단 이유를 함께 표시한다. `mission show`의 `recoveries`를 기준으로 분석 중·보류·실행 중·회차 반환을 구분하며, 회차 반환을 완료로 표시하지 않는다. 정보 부족에는 추가 근거 입력, 중대한 문제에는 질문과 권고, 외부 동의에는 기존 호스트 안내를 제공한다. 재계획 제안에는 현재 작업과 잠금이 유지되고 있음을 표시한다. 이 복구 제어 화면은 설계 단계이며 관련 제어는 [복구 CLI](recovery.md)로 제공한다.

| 상황 | 화면 동작 |
| --- | --- |
| 등록 프로젝트 없음 | 등록·후보 탐색 안내 |
| 빈 그룹 | 프로젝트 추가 버튼, 실행 비활성화 |
| 설치 없음 또는 손상 | 원인과 복구 안내, 개발 실행 비활성화 |
| JSON 버전 미지원 | 호환되지 않는 버전 표시 |
| 최근 조회 실패 | 마지막 성공 관측 값과 실패 시각을 함께 표시 |
| 프로젝트가 이미 작업 중 | 대기 또는 충돌 사유 표시 |
| 일부 프로젝트만 실패 | 성공 결과 유지, 실패 대상 재시도 |
| 서버 재시작 후 관측 불가 | 확인 필요 표시, 재조회 제공 |

시간 초과나 연결 끊김을 완료로 표현하지 않습니다. 긴 목록은 검색·필터·페이지 단위 조회를 제공하고, 필터 뒤 선택이 화면 밖에 남아 있다면 전체 선택 수와 선택 항목 보기를 제공합니다.
